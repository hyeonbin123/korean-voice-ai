# asr-compare: 같은 발화 인식 비교

세 구성 요소(whisper-ko-ft, stt-scratch, voice-translator)가 FLEURS 한국어 test의 발화마다 저장해 둔 인식 결과(가설)를 같은 발화끼리 짝지어, 한 가지 규칙으로 다시 채점해 견주는 명령줄 도구다. 견주는 규칙은 [docs/asr-comparison.md](../../docs/asr-comparison.md)에 있고, 이 문서는 도구를 쓰는 법과 재료를 읽는 방식을 적는다.

- 새로 디코딩하지 않는다. 모델을 올리지 않고 GPU도 쓰지 않으며, 구성 요소가 이미 커밋해 둔 리포트 파일을 읽기만 한다. 재료 파일은 고치지 않는다.
- 실행 의존성이 없다. 파이썬 표준 라이브러리만 쓴다. 이 폴더가 자기 환경(`.venv`)과 잠금(`uv.lock`)을 따로 가져서 구성 요소의 환경(torch 등)과 섞이지 않는다. 잠금에 든 것은 시험과 린트 도구(pytest, ruff)와 그 의존 패키지뿐이다.
- 구성 요소마다 저장한 모양이 다른 가설(정규화한 글, 원문, JSONL)을 같은 정답, 같은 정규화, 같은 글자 오류율, 같은 95% 구간으로 다시 센다.

## 명령 세 개

| 명령 | 하는 일 | 파일을 쓰나 |
|---|---|---|
| `check` | 재료를 읽고 짝짓기 검증 여덟 가지를 돌린다. 검증이 통과하면 이어서 구성 요소가 이미 기록한 값을 저장된 가설에서 다시 세어 묶음마다 한 줄씩 찍는다. 어긋남 줄을 모두 찍고 끝 줄에 요약을 쓴다 | 쓰지 않는다 |
| `run --out <폴더>` | 재료가 고정 목록(`inputs.sha256`)과 같은지 먼저 견주고, 같으면 `check`와 같은 관문(검증과 기록값 재현)을 지나 채점해서 결과 파일 둘을 그 폴더에 쓴다. 어느 쪽에서든 걸리면 줄만 찍고 아무 파일도 만들지 않는다 | `--out` 폴더에만 쓴다 |
| `verify` | `run`과 같이 고정 목록과 관문을 지난 뒤, 저장소의 `evaluation/asr/results/`에 있는 결과 파일 둘이 지금 재료에서 다시 만든 글과 글자까지 같은지 견준다 | 쓰지 않는다 |

세 명령 모두 `--repo <저장소 뿌리>`를 받는다. 기본값은 이 도구가 든 저장소이고, 작업 폴더에 기대지 않는다. `check`는 `--print-inputs`도 받는다(아래 '재료 고정 목록').

종료 코드는 셋이다.

- 0: 통과.
- 1: 어긋남. 재료가 고정 목록과 다르거나(`run`, `verify`), 짝짓기 검증에 걸렸거나, 기록값이 재현되지 않았거나, `verify`에서 결과 파일이 다시 만든 것과 다르다.
- 2: 읽지 못함이거나 잘못된 사용. 재료, 결과 파일, 고정 목록이 없거나 꼴이 틀림, 저장소 폴더가 아님, 결과를 쓰지 못함(쓸 결과 파일이 읽은 재료와 같은 파일인 경우 포함), 잘못된 인자.

읽지 못한 것(2)과 내용이 맞지 않는 것(1)은 다르게 다룬다. 이 도구는 틀린 재료를 고치거나 건너뛰지 않고, 읽은 그대로 검증에 넘겨 어긋남 줄로 알린다. 실패했는데 0으로 끝나는 길은 없다.

세 명령은 같은 관문(짝짓기 검증, 그리고 검증이 통과했을 때만 기록값 재현)을 지난다. 기록값이 재현되지 않는데 결과 파일을 쓰거나 견주는 길은 따로 없다.

## 쓰는 법

저장소의 `evaluation/asr` 폴더에서 한다. 파이썬 3.11 이상과 uv 0.13.1 이상이 필요하다.

```sh
cd evaluation/asr
uv sync --frozen
uv run --frozen --no-sync asr-compare check
uv run --frozen --no-sync asr-compare check --print-inputs
uv run --frozen --no-sync asr-compare run --out results
uv run --frozen --no-sync asr-compare verify
```

`--frozen`은 `uv.lock`을 고치지 않고 그대로 따르게 하고, `--no-sync`는 실행할 때마다 환경을 다시 맞추지 않게 한다. 잠금을 바꿀 수 있는 `uv add`와, `--frozen` 없는 `uv sync`는 쓰지 않는다.

재료가 모두 맞으면 `check`는 묶음마다 재현 줄 한 줄(묶음의 정해진 차례로 열네 줄)과 끝 줄을 찍고 0으로 끝난다. 아래는 줄의 꼴이고, 값 자리는 글로 적었다.

```text
<묶음 키>: 기록 <편집 수의 합>/<정답 글자 수의 합> = 다시 센 <편집 수의 합>/<정답 글자 수의 합>
묶음 14개, 발화 382개(한글 전용 257개), 어긋남 0개
```

재현 줄의 값은 구성 요소가 이미 적어 둔 값이다. 각 구성 요소가 저장한 자기 정답으로 센 편집 수의 합과 정답 글자 수의 합이고, whisper-ko-ft 열 묶음은 리포트에 발화마다 저장된 값과 `summary.error_rate`를 다시 센 값과 견준다. stt-scratch 두 묶음은 한글 전용 발화만 센 기록도 같은 줄에 잇는다(`, 한글 전용 기록 … = 다시 센 …`). 다르면 `=` 대신 `≠`가 찍히고, 합은 같아도 발화별 값이나 오류율이 다르면 그 까닭이 줄 뒤에 붙는다. 어긋남 수는 짝짓기 검증의 어긋남 줄 수와 재현이 다른 묶음 수의 합이다. 검증이 어긋나면 재현은 돌리지 않는다(행을 믿을 수 없다). 이 명령은 묶음을 서로 견주는 값(공통 정답으로 다시 센 값, 구간, 차이)을 만들지 않는다. 그런 값은 `run`만 낸다.

어긋남이 있으면 그 줄들이 요약 앞에 모두 찍힌다(상한이 없고, 짝짓기 검증의 어긋남은 끝 줄의 수와 찍힌 줄 수가 같다). `run`은 통과하면 요약 한 줄을 찍고 이어서 쓴 파일마다 `쓴 파일: <경로>` 한 줄을 찍는다. `verify`는 통과하면 `결과 파일 둘이 다시 만든 것과 같다: <폴더>`를, 다르면 파일 이름과 처음 다른 줄 번호를 찍는다. 두 명령 모두 재료나 관문에 걸리면 `check`와 같은 줄을 찍고 1로 멈춘다.

표준 출력과 오류는 시작할 때 UTF-8과 LF 줄 끝으로 다시 연다. 한국어 Windows에서 파이프나 파일로 받아도 한글이 깨지지 않고 줄 끝에 CR이 섞이지 않는다.

## 재료를 읽는 방식

재료는 저장소 안의 파일 열아홉 개다. 가설 묶음 열네 개의 리포트(voice-translator 둘, whisper-ko-ft 열, stt-scratch 둘), whisper-ko-ft가 같은 가설이라고 적은 형제 리포트 넷, stt-scratch의 매니페스트 하나다. 이 재료 파일의 경로 목록은 `src/asr_compare/sources.py`에 코드로 정해져 있다. 읽는 꼴은 셋이다.

| 구성 요소 | 파일 | 담긴 것 |
|---|---|---|
| voice-translator | JSON(최상위가 길이 1인 목록) | 문장 번호, 음성 길이, 정답, 가설. 글은 이미 정규화돼 있다(공백 없음) |
| whisper-ko-ft | JSON(`summary`와 `utterances`) | 문장 번호(같은 문장의 둘째 녹음부터 `<번호>#<n>`), 음성 길이, 정답, 가설(정규화 전 원문) |
| stt-scratch | 매니페스트(JSONL)와 가설 파일(JSONL) | 매니페스트에 발화 id, 음성 길이, 한글 전용 표시. 가설 파일에 정답과 가설 |

같은 발화는 FLEURS 한국어 test(parquet)의 행 번호로 짝짓는다. stt-scratch는 발화 id의 마지막 수가 행 번호이고, 파일 안 차례에 기대지 않는다. voice-translator와 whisper-ko-ft의 항목에는 행 번호가 없어서 리포트 안의 위치를 행 번호로 받아들인다. 이것은 전제이고, 아래 짝짓기 검증의 문장 번호, 음성 길이, `#n` 표시 검사가 그 증거다. 문장 번호나 파일 안 차례로 짝지으면 조용히 틀릴 수 있다(같은 문장을 두 번 녹음한 발화는 문장 번호가 같다). 이 검사로도 잡지 못하는 틈은 `src/asr_compare/join.py` 머리 설명에 적었다.

읽기는 줄바꿈 변환과 글자 코드에 흔들리지 않는다. 줄바꿈 변환을 켠 채 받은 복제본에서는 같은 파일이 CRLF로 들어오므로, 바이트에서 줄 끝의 CRLF를 LF로 바꾼 뒤 `utf-8-sig`(앞의 BOM은 버린다)로 푼다. 재료의 sha256도 줄 끝을 LF로 맞춘 바이트에서 낸다(BOM은 떼지 않는다). 그래서 LF로 커밋된 파일의 값은 `sha256sum`의 값과 같고(CRLF로 커밋된 파일은 줄 끝의 CR을 뗀 내용의 값이다), 어디서 받은 복제본이든 같은 값이 나온다.

## 재료 고정 목록

`evaluation/asr/inputs.sha256`은 재료 열아홉 개의 sha256을 적어 둔 파일이다. `check --print-inputs`의 출력 그대로이고, 한 줄에 소문자 16진수 sha256 64자, 공백 둘, 저장소 뿌리 기준 경로가 온다(`sha256sum`이 글자 모드로 찍는 꼴과 같다). 줄은 경로 순이고 줄 끝은 LF, 끝 개행은 하나다.

```sh
uv run --frozen --no-sync asr-compare check --print-inputs > inputs.sha256
```

`--print-inputs`는 검증도 기록값 재현도 하지 않고, 재료를 읽을 수 있기만 하면 목록을 찍고 0으로 끝난다(읽지 못하면 2). 이 출력은 파일로 받아 쓰므로 표준 출력의 줄 끝을 바꾸지 않게 연다. 리다이렉션이 UTF-8이 아닌 파일을 만드는 셸(Windows PowerShell 5.1의 `>`가 그렇다)에서는 만들지 않는다. 그렇게 만든 파일은 UTF-8이 아니라서 읽히지 않는다(2).

`run`과 `verify`는 시작할 때, 짝짓기 검증보다 먼저, 이 목록을 읽어 지금 재료와 경로마다 견준다. 같지 않으면 다른 재료마다 한 줄을 찍고 1로 멈춘다. 줄은 경로 순이고 다른 곳은 세 가지다.

```text
<경로>: 값이 다르다(고정 <sha256>, 지금 <sha256>)
<경로>: 고정 목록에 없다(지금 <sha256>)
<경로>: 지금 재료에 없다(고정 <sha256>)
재료 N개가 고정 목록(evaluation/asr/inputs.sha256)과 다르다
```

목록이 없거나 꼴이 틀리면 2다. 꼴이 틀린 경우는 UTF-8이 아님, BOM이 붙음, 줄이 `<sha256>  <경로>`(소문자 16진수 64자, 공백 둘)가 아님, 빈 줄, 같은 경로가 두 번, 적힌 재료가 하나도 없음이다. 줄 끝이 CRLF인 목록은 LF로 보고 읽는다. `check`는 이 목록을 보지 않는다(목록을 만드는 쪽이다).

규칙을 먼저 적고 그 뒤에 재는 일에서, 잰 재료가 규칙을 적을 때의 재료와 같다는 것을 지키려는 것이다. 결과가 다를 때 까닭이 재료인지 도구인지를 출력에서 가르는 데도 쓴다. 재료가 달라졌으면 `verify`는 결과 파일을 견주기 전에 이 대조에서 멈춘다.

## 짝짓기 검증 여덟 가지

표를 만들기 전에 아래 검사가 모두 통과해야 한다. 어긋난 점마다 한 줄이 나오고, 줄에는 묶음 키와 행 번호가 들어간다.

1. 발화 수와 행 번호: 묶음마다 행 번호가 0부터 빠짐없이 한 번씩 나온다. 여기서 어긋나면 뒤 검사를 돌리지 않는다.
2. 문장 번호: 행마다 모든 묶음의 문장 번호가 같다.
3. 음성 길이: 행마다 모든 묶음의 음성 길이가 같다(소수 둘째 자리로 반올림해 견준다).
4. whisper-ko-ft의 id: 같은 문장의 첫 녹음은 `<문장>`, n번째 녹음은 `<문장>#<n>`이다.
5. 정규화한 정답: voice-translator와 whisper-ko-ft 묶음의 정규화한 정답이 모든 행에서 공통 정답과 같다.
6. stt-scratch의 정답: 정규화한 정답이 공통 정답과 다른 행의 집합이 알려진 행과 정확히 같다.
7. 같은 가설 리포트: 같은 가설이라고 적힌 형제 리포트의 가설이 모든 행에서 글자까지 같다.
8. 한글 전용 표시: 길이가 발화 수이고, 참인 개수가 한글 전용 발화 수와 같다.

1번부터 5번까지는 형제 리포트에도 같은 범위로 건다(7번이 형제 리포트의 가설을 행 번호로 견주기 때문이다).

## 채점 규칙 요약

- 정답: 모든 묶음을 공통 정답으로 센다. 공통 정답은 whisper-large-v3-turbo 묶음의 정답이다. 다른 묶음이 자기 정답을 어떻게 저장했든 그것으로는 세지 않는다(5, 6번 검사가 정규화한 정답이 같음을 확인한다).
- 정규화: 정답과 가설에 똑같이, 소문자로 바꾸고 `[^\w\s']|_`에 맞는 글자와 작은따옴표를 공백으로 바꾼 뒤 모든 공백을 지운다. 세 구성 요소의 한국어 채점 정규화와 같은 규칙이고, 시험이 세 구성 요소의 소스에서 정규식이 글자 그대로 같은지 확인한다.
- 글자 오류율: 정규화한 글자 단위 편집 거리(치환, 삭제, 삽입의 비용이 모두 1)의 합을 정규화한 정답 글자 수의 합으로 나눈다. 발화별 비율의 평균이 아니라서 긴 발화가 글자 수만큼 더 반영된다.
- 범위 둘: 전체와 한글 전용(숫자와 라틴 문자가 없는 발화).
- 95% 구간: 발화를 다시 뽑는 부트스트랩이다. n개에서 n개를 되돌려 뽑는 일을 1,000번 하고, 정렬한 값의 아래에서 25번째와 975번째를 쓴다. 난수는 `random.Random(0)`의 `random()`만 쓰고, 다시 뽑기 번호는 모든 묶음과 모든 짝이 같은 것을 쓴다. 이 구간은 구성 요소가 기록한 구간과 난수 생성기가 달라서 자릿수까지 같지는 않다.
- 짝 비교: 앞 묶음에서 뒤 묶음을 뺀 값이다. 차이의 95% 구간은 같은 다시 뽑기에서 낸 두 글자 오류율의 차이로 구하고, 발화마다 앞 묶음의 편집 수가 뒤 묶음보다 적은, 많은, 같은 발화의 수를 함께 센다.

| 짝 | 앞 | 뒤 | 뜻 |
|---|---|---|---|
| `decoding-path` | whisper-large-v3-turbo | voice-turbo | 같은 이름의 모델을 다른 도구로 디코딩한 두 실행 |
| `vad` | voice-turbo | voice-turbo-vad | voice-translator의 두 실행: 음성 구간 검출을 끈 것(앞)과 켠 것(뒤) |
| `both` | whisper-large-v3-turbo | voice-turbo-vad | 위 둘이 모두 다른 두 실행 |

## 결과 파일

`run`은 같은 이름의 파일 둘을 쓴다. 저장소에 커밋해 두는 자리는 `evaluation/asr/results/`이고 `verify`가 그 자리를 읽는다. 결과 파일을 처음 커밋하기 전에는 그 폴더가 없고, 그동안 `verify`는 2로 끝난다. `--out`을 재료가 든 폴더로 주어서 쓸 파일이 읽은 재료와 같은 파일이 되면(whisper-ko-ft의 재료도 이름이 `fleurs-ko-test.json`이라서 `whisper-ko-ft/reports/<묶음>`을 주면 그렇다) `run`은 쓰기 전에 표준 오류에 한 줄을 찍고 2로 끝나며 결과 파일 둘을 모두 쓰지 않는다. 같은 파일이 아니면 재료가 든 폴더나 저장소 안의 폴더에도 쓴다.

- `fleurs-ko-test.json`: 형식 이름 `asr-compare/1`, 발화 수와 한글 전용 발화 수, 읽은 재료의 경로와 sha256(`inputs`), 묶음마다 범위 둘의 편집 수, 정답 글자 수, 글자 오류율, 95% 구간(`systems`), 짝마다 범위 둘의 차이, 95% 구간, 앞이 적은, 많은, 같은 발화 수(`pairs`).
- `fleurs-ko-test.md`: 같은 내용을 표 셋(전체, 한글 전용, 짝 비교)으로 쓴 글. 판정 문구는 넣지 않는다.

같은 재료에서는 언제나 같은 바이트가 나온다(난수 시드와 키 차례가 고정이고, 집합을 돌며 글을 만들지 않는다). 파일은 UTF-8, BOM 없음, LF 줄 끝으로 쓰고, `verify`는 줄 끝이 CRLF인 복제본(줄바꿈 변환을 켠 채 받은 것)도 LF로 보고 견준다. 비율은 반올림하기 전의 값에서 글마다 한 번만 반올림한다(JSON은 소수 여섯째 자리, Markdown의 퍼센트는 소수 둘째 자리). 재료가 고정 목록과 달라지면 `verify`는 결과 파일을 견주기 전에 그 재료를 경로마다 알리고 1로 멈춘다. 고정 목록을 새 재료에 맞게 다시 만들었는데 결과 파일이 옛 재료로 만든 것이면 결과 파일이 다시 만든 것과 달라서 1로 끝나고, 그때 어느 재료가 달랐는지는 결과 파일의 `inputs`에 적힌 sha256으로 확인한다.

## 폴더 구성

```text
evaluation/asr/
  pyproject.toml, uv.lock   이 폴더의 환경과 잠금
  inputs.sha256             재료 열아홉 개의 sha256(`check --print-inputs`의 출력, 재료 고정 목록)
  src/asr_compare/
    sources.py              재료 읽기(세 꼴)와 sha256
    join.py                 짝짓기 검증 여덟 가지
    recorded.py             구성 요소가 이미 기록한 값의 재현(기록값 사전)
    score.py                정규화, 편집 거리, 다시 뽑기와 95% 구간
    report.py               결과 사전과 JSON, Markdown 글
    cli.py                  명령줄(check, run, verify)과 고정 목록 대조
  tests/                    시험
  results/                  커밋한 결과 파일의 자리(처음 커밋하기 전에는 없다)
```

## 시험과 린트

```sh
cd evaluation/asr
uv run --frozen --no-sync pytest -q
uv run --frozen --no-sync ruff check .
uv run --frozen --no-sync ruff format --check .
```

시험은 대부분 같은 꼴로 만든 합성 저장소를 임시 폴더에 만들어 돌린다. 예외는 둘이다. `tests/test_scoring_rule.py`는 세 구성 요소의 정규화 소스 글을 읽어 정규식이 이 도구의 것과 같은지 확인한다. `tests/test_real_inputs.py`는 저장소의 실제 리포트 파일을 읽기만 해서 결합 검증과, 구성 요소가 이미 기록한 값의 재현만 본다(새 수치를 내지 않는다). 그래서 시험은 저장소 전체가 있는 곳에서 돌려야 하고, 재료 파일이 없으면 건너뛰지 않고 실패한다.
