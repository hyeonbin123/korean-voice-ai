# 서비스 (3단계)

평가에서 쓰는 에이전트 루프와 도구를 그대로 웹 채팅으로 돌린다. 달라지는 것은 DB가 남는다는 점(PostgreSQL), 대화가 요청 사이에 저장된다는 점, 큰 환불은 사람이 승인한다는 점이다.

## 실행

모델은 호스트의 Ollama가 돌린다 (GPU가 필요해서 컨테이너에 넣지 않았다).

```bash
ollama pull qwen3.5:4b
docker compose up --build
```

- 에이전트 모델은 `qwen3.5:4b`, 비사고 모드다 (2026-10-04부터. 그 전에는 `qwen2.5:7b-instruct`). 이유와 알려진 위험은 아래 "정한 것과 이유"의 첫 항목

- 채팅: http://127.0.0.1:8062
- 관리 화면: http://127.0.0.1:8062/admin (토큰은 `ADMIN_TOKEN`, 기본값 `local-admin`)
- DB: `127.0.0.1:55462` (PostgreSQL 16)
- 포트는 모두 127.0.0.1에만 연다. 기본 비밀번호와 토큰은 로컬 시연용이다. 바꾸려면 `.env.example`을 `.env`로 복사해 값을 넣는다. DB 비밀번호는 앱의 DB 주소에 그대로 들어가므로 영문·숫자와 `- _ . ~`만 쓴다 (`@`나 `%`가 들어가면 주소가 잘못 읽혀 앱이 DB에 붙지 못한다). (2026-11-24 보탬) 포트를 127.0.0.1에만 여는 것만으로는 브라우저를 거치는 경로를 막지 못한다: 공격자 페이지의 이름을 공격자의 DNS가 127.0.0.1로 다시 풀면(DNS 리바인딩) 그 페이지의 요청이 같은 출처로 이 포트에 닿는다. 그래서 서비스는 `Host` 헤더가 허용 목록(기본 `127.0.0.1`과 `localhost`, 포트는 보지 않는다)에 없으면 400을 돌려준다. 다른 이름으로 접속해야 하면(앞단 프록시의 이름 등) `ALLOWED_HOSTS`(Compose는 `.env`의 `ALLOWED_HOSTS`)에 쉼표로 구분해 더한다 (아래 "정한 것과 이유"의 'Host 헤더')
- 처음 뜰 때 마이그레이션(Alembic)을 돌리고, 쇼핑몰 테이블이 비어 있으면 평가와 같은 생성 데이터를 넣는다. 채팅 화면 아래에 시험해 볼 고객 이름과 전화번호가 나온다
- 모델은 처음 쓸 때 Ollama가 올린다. 그래서 띄운 직후의 첫 메시지와, 모델이 `KEEP_ALIVE`(기본 60분) 동안 쓰이지 않아 내려간 뒤의 첫 메시지는 모델을 올리는 시간만큼 늦다 (이 PC의 D: HDD에서 첫 호출 55초. 아래 "qwen2.5 7B로 써 보면" 절의 `qwen3.5:4b` 확인. 그동안 화면에는 진행 표시가 뜨고, 호출 하나의 제한 시간은 10분이다). 다른 프로그램이 같은 Ollama에 다른 모델을 올리면 그보다 일찍 내려갈 수 있다. 시작할 때 미리 올리려면 `PRELOAD=1`(`.env`. 호스트에서는 `SUPPORT_AGENT_PRELOAD=1`): 서비스가 뜨면서 작업 스레드에서 모델을 한 번 올리고 걸린 시간을 서버 로그(`docker compose logs app`)에 한 줄 남긴다. 시작은 그것을 기다리지 않고, 실패해도(Ollama가 꺼져 있음 등) 경고 한 줄만 남기고 그대로 뜬다. 오래 두려면 `KEEP_ALIVE`: Ollama의 `keep_alive` 형식 그대로다(단위가 붙은 기간 `24h`·`1h30m`, 초 단위 정수 `3600`, 음수 `-1`은 내리지 않음, `0`은 답한 뒤 바로 내림). 읽을 수 없는 값은 서비스가 시작할 때 거절한다. 기본값(60분, 미리 올리지 않음)은 이 설정이 생기기 전과 같다: GPU를 다른 작업과 나눠 쓰므로 고객이 없을 때 모델이 자리를 오래 쥐지 않게 한다 (2026-10-30 추가)
- 앱 컨테이너는 권한을 줄여 뜬다 (`compose.yaml`, 2026-10-30부터): Linux capability를 모두 빼고(`cap_drop: ALL`. 비루트 사용자가 8000번에서 듣는 데 필요한 것이 없다), setuid 실행 파일로 권한을 얻지 못하게 하며(`no-new-privileges`), 루트 파일 시스템은 읽기 전용이다(쓸 수 있는 곳은 메모리 위의 `/tmp`뿐. 이 구성의 앱은 저장할 것을 모두 PostgreSQL에 쓴다). 메모리 한도는 2 GB다. 빈 DB에서 처음 뜨기(마이그레이션과 생성 데이터)와, 같은 설정의 컨테이너에서 오프라인 대역(아래)으로 본인 확인·취소·사람 승인을 한 번씩 지나 보는 것까지 확인했다. 서버는 접근 로그를 끄고 뜬다 (아래 "세션 id가 곧 열쇠다")

Docker 없이 SQLite 파일로도 돈다.

```bash
uv run uvicorn support_agent.service.app:create_app --factory --port 8062 --no-access-log
```

설정은 환경 변수로 한다 (`SUPPORT_AGENT_` 접두사, `service/settings.py`): `DATABASE_URL`, `OLLAMA_URL`, `MODEL`, `THINK`, `NUM_CTX`, `KEEP_ALIVE`, `PRELOAD`, `POLICY`, `CLAIMS`, `GUARD`, `ERRORS`, `REPEAT`, `NOW`, `APPROVAL_REFUND_WON`, `ADMIN_TOKEN`, `MAX_MESSAGE_CHARS`, `MAX_AGENT_CALLS_PER_TURN`, `MAX_TURNS_PER_SESSION`, `LOAD_SEED`, `EXPOSE_OPENAPI`, `VOICE`, `TTS_DEVICE`, `STT_DEVICE`, `MAX_AUDIO_BYTES`, `MAX_AUDIO_SECONDS`, `MAX_TTS_CHARS`, `MAX_CONCURRENT_TURNS`, `MAX_CONCURRENT_SPEECH`, `ALLOWED_HOSTS`, `SUMMARY_URL`, `SUMMARY_TIMEOUT_S`. 범위 밖 값은 서비스가 시작할 때 거절한다 (아래 "한도"의 설정 범위). (2026-11-05 보탬) `LOAD_SEED`·`EXPOSE_OPENAPI` 두 설정이 이 목록에 빠져 있어 넣었다. `LOAD_SEED`(기본 켬)는 위 "처음 뜰 때" 줄의 생성 데이터 넣기를 켜고 끈다: 끄면 마이그레이션만 하고 생성 데이터를 넣지 않아 빈 DB면 빈 쇼핑몰로 뜬다 (MCP 서버도 같은 설정을 읽는다). `EXPOSE_OPENAPI`(기본 끔)는 API 설명(`/openapi.json`)을 내놓는다 (아래 "모델 없이 띄우기, 보안 스캔"). 이 목록이 설정과 같은지는 `tests/test_deploy_config.py`가 확인한다. (2026-11-24 보탬) `ALLOWED_HOSTS`(기본 비어 있음)는 서비스가 `Host` 헤더로 받는 이름을 기본 `127.0.0.1`·`localhost` 뒤에 더하는 설정이다: 쉼표로 구분한 호스트 이름이나 IPv4 주소만 받고, 포트·`http://`·경로·와일드카드(`*`)·IPv6 주소·빈 항목은 서비스가 시작할 때 거절한다 (아래 "정한 것과 이유"의 'Host 헤더').

## 구성

```
브라우저 ── POST /api/sessions/{id}/messages (SSE) ──> app.py ──> core.ChatService.handle()
                                                                    │  agent.agent_turn()   평가와 같은 루프
                                                                    │  toolkit.execute()    평가와 같은 도구, 같은 단일 경로
                                                                    │    └ on_success = 승인 관문, 감사 행 (도구와 같은 트랜잭션)
                                                                    ▼
                                         PostgreSQL: 쇼핑몰 테이블 13개 + chat_sessions, audit_events, approvals
```

| 파일 | 하는 일 |
|---|---|
| `service/settings.py` | 환경 변수 설정 |
| `service/store.py` | 서비스 테이블 3개. 쇼핑몰 테이블과 메타데이터를 나눠서 판정용 덤프(`db.dump_db`)에는 들어가지 않는다 |
| `service/bootstrap.py` | 엔진 생성, Alembic 마이그레이션, 빈 DB에 생성 데이터 복사 |
| `service/core.py` | 한 턴 처리, 감사 로그, 승인 대기열. 웹 코드가 없어 테스트가 직접 부른다 |
| `service/app.py` | FastAPI: SSE 채팅, 관리자 API, 정적 화면 |
| `service/summary.py` | 상담 후처리 서비스(이 저장소의 call-summary)를 부르는 클라이언트 (2026-11-25 추가, 아래 "상담 후처리 기록") |
| `service/migrations/` | Alembic. 테스트가 "마이그레이션 결과 = 선언한 테이블"을 확인한다 |

## 모델 없이 띄우기, 보안 스캔

```bash
uv run uvicorn support_agent.service.offline:create_offline_app --factory --port 8062
```

- `service/offline.py`는 모델 자리에 규칙 몇 줄짜리 대역을 넣는다 (이름과 전화번호를 보면 본인 확인, 주문 번호를 보면 조회, "취소"가 있으면 취소). 나머지는 실제 코드 그대로라 화면 작업, 웹 계층의 보안 스캔, 스모크 테스트를 GPU 없이 할 수 있다. `SUPPORT_AGENT_VOICE=1`이면 음성 끝점도 음성 모델 없는 대역으로 응답한다
- 이 절의 오프라인 앱 명령은 실제 서비스 명령과 달리 접근 로그를 켠 채 둔다. 실제 고객이 없는 시험용이고, 보안 스캔 기록(아래 표)의 요청 수와 경로별 응답 코드를 이 로그에서 센다. 실제 고객을 받는 서비스는 접근 로그를 끈다 (아래 "세션 id가 곧 열쇠다")
- API 설명(`/openapi.json`)은 `SUPPORT_AGENT_EXPOSE_OPENAPI=1`일 때만 내놓는다. 스캐너가 경로와 본문 형태를 정확히 알게 하려는 것이고, 평소에는 꺼 둔다
- HawkScan(StackHawk) 설정은 `stackhawk.yml`이다. 비밀값은 없고 `APP_ID`, `ADMIN_TOKEN`, `SCAN_SESSION_ID`를 환경 변수로 받는다. 관리자 API는 `X-Admin-Token` 헤더를 미리 넣어 주는 방식으로 인증하고, 스캐너가 지어낸 세션 번호로는 "없는 세션"(404)에서 끝나므로 스캔 전에 만든 실제 세션 번호와 승인 번호를 `customVariables`로 넣어 준다

```bash
export SUPPORT_AGENT_EXPOSE_OPENAPI=1 SUPPORT_AGENT_VOICE=1 SUPPORT_AGENT_ADMIN_TOKEN=<임의의 토큰>
uv run uvicorn support_agent.service.offline:create_offline_app --factory --port 8062
# 다른 창에서: 세션을 하나 만들고(POST /api/sessions) 큰 금액 취소를 요청해 승인 대기를 하나 만든 뒤
APP_ID=<앱 번호> ADMIN_TOKEN=<같은 토큰> SCAN_SESSION_ID=<세션 번호> hawk scan
```

- **2026-10-05부터는 OWASP ZAP(무료, Apache-2.0)으로 스캔한다.** HawkScan은 체험 기간이 이날 끝났다. 설정은 `zap/automation.yaml`로 같은 스캔이다 (API 설명, 스파이더, 패시브 스캔, 기본 정책의 액티브 스캔). ZAP 2.17.0 공식 크로스플랫폼 패키지를 Java 17 이상으로 직접 돌린다 (Docker 없음). 관리자 토큰은 ZAP이 대상 호스트로 가는 모든 요청에 헤더를 붙이게 하는 환경 변수(`ZAP_AUTH_HEADER*`, `zap/run_zap.sh`가 정함)로 넘기고, 실제 세션·승인 번호는 `requestor` 작업이 그 번호로 요청을 한 번씩 보내 스캔 대상에 넣는다 (HawkScan의 `customVariables` 자리. 승인 결정 요청은 그 승인을 실행한다). 두 도구는 규칙 목록과 기본 설정이 달라 **결과를 직접 비교하지 않고, 같은 도구의 기록끼리만 비교한다**

```bash
# 위와 같이 오프라인 앱을 띄우고 세션과 승인 대기를 만든 뒤. ZAP_DIR은 zap-2.17.0.jar가 있는 폴더, 결과는 work/zap/<이름>/
ZAP_DIR=<폴더> ADMIN_TOKEN=<같은 토큰> SCAN_SESSION_ID=<세션 번호> SCAN_APPROVAL_ID=<승인 번호의 숫자> bash zap/run_zap.sh <이름>
```

- ZAP의 액티브 스캔은 실제 세션에 메시지를 수백 번 보낸다. 기본 설정이면 세션이 40턴에서 닫히고 그 뒤의 공격 요청은 처리기에 닿지 못한 채 409로 끝나므로(8차), 대상은 세션당 턴 한도를 크게 주고 띄운다: `SUPPORT_AGENT_MAX_TURNS_PER_SESSION=100000` (9차부터). 승인 결정 요청은 `requestor`가 그 승인을 실행한 뒤라 나머지는 이미 결정된 승인의 409로 끝난다 (결정 처리기를 끝까지 지나는 것은 첫 요청뿐)
- 같은 PC에서 다른 ZAP이 프록시 포트 8080을 쓰고 있으면 `ZAP_PORT=8091`처럼 ZAP 자신의 포트만 바꿔 띄운다 (스캔 대상 주소와는 상관없다)

스캔 결과 (2026-09-21\~11-26. 1\~7은 HawkScan 6.4.0, 정책 OpenAPI/REST API. 8부터 OWASP ZAP 2.17.0, 기본 정책. 1\~3은 2026-09-21, 4\~17의 날짜는 각 줄에. 도구가 바뀐 8부터는 1\~7과 직접 비교하지 않는다)

High 1(40024, 메시지의 `text`)이 나왔고 16행에 없던 규칙 번호다. 17행에 적은 대로 이 경보는 13행과 같은 꼴이고, 13행이 정한 단일 스레드 재시험에서 응답 시간이 N에 따라 늘지 않아 시간 휴리스틱의 오탐으로 분류했다. 서비스 코드와 스캔 설정에서 고칠 것은 찾지 못했다. 그래서 18차는 17차와 같은 대상·설정·부하 조건으로 한 번 더 돌리고, 40024가 같은 자리에 다시 나올 때의 판정을 여기 먼저 정한다. 대상: 17차 대상 `dc7067e`와 같은 코드다(그 뒤의 커밋은 이 문서뿐이어야 한다. `src/`·잠금 파일·`zap/`가 바뀌었으면 이 단락으로 돌리지 않는다). 구성, `zap/automation.yaml`, 부하 조건, 기다리는 규칙, 부하 기록은 위 "(2026-11-25 보탬, 17차 스캔 전)"과 같다. 통과 조건(모두 맞아야 통과다)도 그 단락의 (1)\~(8)과 같고, 비교 기준은 그대로 16행이다(17행은 통과하지 못한 줄이라 기준 행으로 쓰지 않는다). 한 가지만 다르다: 40024가 메시지(`POST /api/sessions/{id}/messages`)나 답 읽어 주기(`POST /api/sessions/{id}/speech`)의 `text`에 나오면(13행과 17행에서 본 자리) 스캔 뒤 같은 코드·설정의 앱을 그 스캔의 DB 사본으로 띄워 13행의 재시험을 한다: 스레드 하나로 원문 `O-10097`과 `case randomblob(N) when not null then 1 else 1 end` 본문 넷(N=10⁶·10⁷·10⁸·10⁹)을 5회씩 번갈아 그 끝점에 보낸다. 재시험의 판정(스캔 전에 정한다): (가) 모든 요청의 상태 코드가 본문과 상관없이 같고(메시지는 200, 답 읽어 주기는 상담원이 한 말이 아닌 글을 거절하는 403), 메시지라면 저장된 고객 메시지가 보낸 글 그대로이며(앞뒤 공백만 뗌) (나) N=10⁸ 본문의 응답 시간 중앙값이 N=10⁶ 본문의 중앙값에 250 ms를 더한 것보다 작고 (다) N=10⁹ 본문의 중앙값이 원문의 중앙값에 1,000 ms를 더한 것보다 작으면, 그 경보를 시간 휴리스틱의 오탐으로 분류하고 (1)과 (2)에서 세지 않는다. 문턱의 근거: 스캔하는 PC의 SQLite가 `randomblob(10⁸)`을 실제로 만드는 데 317 ms가 걸렸다(10⁶은 3 ms, 10⁷은 33 ms. 17행). 주입이 일어났다면 10⁸ 본문은 10⁶ 본문보다 그만큼, 10⁹ 본문은 그 열 배쯤 더 걸린다. 셋 가운데 하나라도 맞지 않으면 그 경보는 그대로 High이고 통과가 아니다. 다른 자리의 40024, 다른 규칙의 High·Medium, 16행에 없는 그 밖의 규칙 번호는 재시험 없이 통과가 아니다. 재시험을 했으면 그 수치와 분류를 18행에 적고, 보고서에 High가 남아 있다는 사실도 그대로 적는다. 판정과 그다음(통과하지 못했을 때 결과를 그대로 적고 다음 기준을 먼저 적는 것)은 17차 전 단락과 같다. 결과를 본 뒤 이 단락의 조건을 고치지 않는다.

스캔하지 못한 것: 실제 모델이 붙은 경로(모델의 출력이 도구 인자로 들어가는 길)는 DAST의 대상이 아니라 평가 환경의 몫이다. 음성 끝점은 대역으로만 확인했다 (실제 디코더에 들어가는 조작된 음성 파일은 다루지 못했다).

## 정한 것과 이유

- **기본 모델은 `qwen3.5:4b`, 비사고 모드다 (2026-10-04부터).** 8단계 측정(`experiments.md` 8단계)에서 서비스 구성(P1) 그대로 에이전트 모델만 바꿨을 때 시험용 40과제 × 4회의 pass^1이 18.1%(qwen2.5 7B)에서 55.6%로 올랐다 (+37.5%p [+28.7, +46.2]). 7B가 0%였던 복합 과제가 31.2%가 됐고, 도구 호출을 본문에 쓰는 형식 오류는 84 → 0, 한자가 섞인 답은 2.9% → 0.4%다. 에이전트 호출당 시간은 1.24배(559 → 693 ms)다. 측정 규칙은 그 단계에서 서비스를 바꾸지 않게 정해 두었고, 결과표를 보고 사용자가 2026-10-04에 바꾸기로 정했다
  - **알려진 위험**: 시험용 과제에서 새 모델은 과제가 요구하지 않은 쓰기를 **13건** 했다. 이전 서비스 구성(qwen2.5 7B, P1)은 **6건**이었다. 새 모델은 훨씬 자주 행동해서(성공한 쓰기 27 → 100건) 쓰기 정밀도는 78% → 87%로 올랐지만, 잘못된 쓰기의 건수는 두 배다. 통과된 규정 위반은 두 구성 모두 0건이다 (도구가 막는다). 13건은 도구의 규정 검사를 통과한, 과제가 요구하지 않은 쓰기다. 큰 환불의 사람 승인(아래)은 그대로 켜 두지만 **이 13건에는 안전장치가 되지 못한다**: 시험용 기록을 다시 세어 보면 13건 모두 환불액이 10만 원 미만(가장 큰 것 83,500원)이거나 환불이 없는 쓰기(교환, 보상 쿠폰, 티켓, 상담원 연결)라 승인 관문에 걸리는 것이 0건이다. 승인 관문이 잡는 것은 환불액 10만 원 이상인 취소·반품뿐이라, 그보다 작은 환불과 다른 쓰기(교환, 배송지 변경, 보상 쿠폰, 상담 티켓)의 잘못된 처리는 막지 못하고 감사 로그에 남는다
  - `THINK`는 Ollama 요청의 `think` 값이다 (`on`, `off`, `omit` = 보내지 않음). 비워 두면 기본 모델에는 `off`(잰 그대로), 다른 모델에는 `omit`이다. 사고 모드가 없는 모델은 이 값을 거부할 수 있어서다. 이전 모델로 돌아가려면 `MODEL=qwen2.5:7b-instruct`만 바꾸면 된다 (Compose는 `.env`의 `MODEL`). 사고 모드가 있는 다른 모델을 쓰면 `THINK=off`를 함께 준다
  - 잰 구성과 다른 점: 서비스의 `num_ctx`는 16384다 (8단계는 12288로 쟀다. num_ctx는 KV 캐시의 크기와 대화가 닫히는 한도를 정한다). 고객이 시뮬레이터가 아니라 사람이고, 언어 가드(L1)가 켜져 있다. 음성 모드(V2 규칙)와 완료 주장 가드(C1)는 이 모델로 재지 않았다 (5단계·7단계는 qwen2.5 7B로 쟀다)
- **도구가 규정을 막는다 (P1).** 2단계 측정에서 P1은 성공률을 올리지 못했지만 통과된 규정 위반을 12건에서 0건으로 줄였다. 서비스에서 잘못된 환불은 돈이 나가는 일이라, 코드로 확인할 수 있는 규정은 모델을 믿지 않고 도구에서 막는다.
- **한국어가 아닌 답은 고객에게 보내지 않는다.** qwen2.5는 한국어 대화 도중에 중국어로 넘어가는 일이 있다 (개발용 기록에서 7B는 답 1,083개 중 12개, 14B는 801개 중 24개. 서비스를 실제 모델로 확인할 때도 나왔다. 2026-10-04부터의 기본 모델 qwen3.5 4B는 8단계 시험용 기록에서 답 1,667개 중 7개). 서비스는 한자나 가나가 두 글자 이상 든 답을 형식 오류처럼 돌려보내고 한국어로 다시 답하게 한다 (`RunConfig.language = "L1"`). 재시도를 다 쓰고도 안 되면 정해진 한국어 안내 문장이 나간다. 이 가드는 측정하지 않았다. 평가의 기본값은 끈 상태(`L0`)다. 2026-10-15 개발용 기록에 같은 검출기를 대 보니 `qwen3.5:4b`의 본문 답 848개 중 3개만 걸려(실패한 에피소드 1) 성공률 영향은 많아야 +1.0%p라, GPU로 재지 않고 닫았다 (`experiments.md` "닫은 후보")
- **완료 주장 가드는 설정이다 (`CLAIMS`, 기본 `C0`).** 켜면 "취소가 완료되었습니다"처럼 끝났다고 말하는 답을 그 대화의 성공한 도구 결과(승인 대기열에 올라간 요청은 "접수되었다"는 말의 근거)와 대조하고, 근거가 없으면 고객에게 보내지 않고 다시 시킨다. 개발용 측정에서 기본값으로 켜는 조건에 들지 못해 꺼 두었다 (`experiments.md` 7단계). 7단계는 qwen2.5 7B로 쟀고, 2026-10-18에 기본 모델(qwen3.5 4B)로 다시 쟀다 (13단계): 거짓 완료의 전달은 5 → 0이지만 개발용 정답에 없는 쓰기가 3 → 4로 한 건 늘어 재기 전에 정한 켜는 조건을 만족하지 못해 기본값은 그대로 `C0`이다. 승인이 실행되면 그 결과가 대화에 도구 결과로 남으므로, 그 뒤의 "처리되었습니다"는 근거가 있다
- **13단계 후보는 설정이다 (`GUARD`·`ERRORS`·`REPEAT`, 기본 `G0`·`E0`·`D0`, 2026-10-15부터).** `GUARD=G1`은 "확인해 보겠습니다"만 하는 답을, `REPEAT=D1`은 바로 앞에 보낸 답과 같은 답을 고객에게 보내지 않고 다시 시킨다. `ERRORS=E1`은 규정이 막은 쓰기의 오류 글 끝에 그 검사가 쓴 사실(수령·출고 시각, 접수 마감일, 이미 발급된 쿠폰과 발급 시각, 도착 예정일)을 붙인다 (MCP로 부른 도구의 오류 글도 같다). 2026-10-18에 이 모델로 쟀고(`experiments.md` 13단계) 시험용 판정이 "개선을 확인하지 못함"(E1 +1.9%p [−0.6, +4.4])이라 재기 전에 정한 규칙대로 기본값은 모두 끔 그대로다. D1은 개발용에서 −9.4%p로 나빠졌다
- **응답은 이벤트 단위로 흘린다.** 글자 단위가 아니다. 에이전트의 응답은 고객에게 가기 전에 검사를 거친다(도구 호출이 본문에 샌 응답, 잘린 응답은 전달하지 않고 다시 시킨다). 글자를 먼저 흘리면 이 검사를 할 수 없다. 대신 도구를 부를 때마다 "주문 조회 중" 같은 진행 이벤트를 보낸다. 이벤트: `status`, `tool`, `tool_result`, `approval`, `error`, `reply`, `end`.
- **브라우저가 끊겨도 턴은 끝까지 간다.** 도구가 DB를 바꿨는데 대화 기록이 없는 상태를 만들지 않기 위해서다.
- **사람 승인.** 환불액이 기준(기본 10만 원) 이상인 취소·반품은 바로 실행하지 않는다. 환불액은 도구의 규정 계산이 끝나야 알 수 있으므로, 관문은 도구의 트랜잭션 안에 있다: 핸들러가 계산한 실제 `refund_won`이 기준 이상이면 그 트랜잭션을 롤백하고 승인 대기열에 올린 뒤 에이전트에게 `approval_required` 오류로 알린다. 미리 계산해 보는 단계가 따로 없으므로 "확인할 때는 기준 아래였는데 실행할 때는 위"인 틈이 없다. 같은 요청을 다시 호출해도 대기열에는 하나만 남는다. 같은 요청인지는 세션 안에서 대상(도구, 주문, 반품이면 줄 번호)으로 본다: 2026-10-15까지는 인자 전체를 비교해 사유만 바꾼 재요청이 같은 주문의 승인을 하나 더 만들었다. 이제는 처음 요청의 승인 번호를 다시 쓰고, 감사 로그의 `approval_requested`에 `reused`로 남긴다.
  - 반품은 같은 주문에 이미 접수된 반품의 환불액을 더해 기준과 비교한다. 줄을 한 번에 하나씩 나눠 접수해도 합계가 기준에 닿는 반품부터는 사람이 승인한다. 합계가 이미 기준 이상인 주문은 앞의 반품이 승인을 거쳤더라도 그 뒤의 반품도 모두 사람에게 간다. 승인하면 그 호출의 환불액만 처리된다.
  - 승인하면 그때 도구를 실행한다. 그 사이 주문 상태가 바뀌어 도구가 거절하면 `failed`로 남는다.
  - **승인 대기에 걸린 턴에는 서비스의 정해진 안내 문장이 붙는다 (2026-10-05부터).** 예: "주문 O-10097의 취소 요청(환불 예정 108,200원)은 담당자 승인이 필요해 아직 처리되지 않았습니다. 승인 번호는 AP-1이며, 담당자가 확인한 뒤 결과를 이 대화창으로 안내해 드립니다." 에이전트가 읽는 도구 결과(`approval_required`)는 그대로이고, 거기에는 에이전트에게만 하는 지시("고객에게 …라고 알리세요", "같은 요청을 다시 호출하지 마세요")가 들어 있다. 실제 모델이 이 지시를 고객에게 거의 그대로 옮긴 일이 있어서(아래 "qwen2.5 7B로 써 보면"의 큰 취소), 그 턴에 고객이 받는 답은 **모델의 답에서 지시를 옮긴 부분을 뺀 것(남는 것이 있을 때) 뒤에 정해진 안내 문장**이다. 같은 턴에 모델이 조회해 알려 주는 내용, 고객에게 묻는 말, 승인에 걸리지 않은 다른 쓰기의 결과(한 주문의 반품 두 줄 가운데 한 줄만 승인에 걸린 경우 등)는 모델만 말할 수 있으므로 그대로 간다.
    - 빼는 규칙(`service/core.py`의 `without_agent_only`): 지시와 글자·숫자가 10자 이상 이어서 같은 부분(공백과 문장부호는 빼고 보며, 문장이나 줄을 넘어 이어져도 잡는다)이나 "호출"이 든 문장을 뺀다. 그 문장이 "…고, …며, …지만, …는데" 뒤의 쉼표로 절이 나뉘어 있으면 지시와 6자 이상 같은 절만 빼고 나머지 절은 남긴다 (절마다 그 절의 글자만 보고 정한다. 10자 일치가 쉼표를 넘어 앞 절에 걸쳐도 앞 절은 남는다: "1번 상품 반품은 접수되었으며, 결과는 이 대화창으로 안내됩니다." → "1번 상품 반품은 접수되었으며.", 2026-10-05 고침). 예: "1번 상품 반품은 접수되었고(환불 예정 90,400원), 2번 상품은 담당자 확인 후 처리되며 결과는 이 대화창으로 안내됩니다." → "1번 상품 반품은 접수되었고(환불 예정 90,400원)." 쉼표 없이 이어진 절, 조건(…면)·이유(…서)·인용(…다고)으로 이어진 절은 경계를 믿을 수 없거나 떼어 내면 남은 절이 원래 문장보다 많은 것을 말하게 되므로 문장째 뺀다. 남은 절은 "…고."처럼 이음 어미로 끝날 수 있다
    - 대화 기록에는 고객이 받은 글 그대로가 에이전트의 답으로 남아, 다음 턴의 모델도 고객이 읽은 것을 읽는다. 모델이 쓴 원래 답은 감사 로그 `agent_reply`의 `not_delivered`에만 남는다
    - **2026-10-24부터는 턴이 어떻게 끝나도 붙는다.** 승인 대기에 쓰기를 올린 턴이 모델의 답이 아니라 상담원 연결, 컨텍스트 한도, 턴당 호출·재시도·도구 오류 한도, 예외(모델 연결 오류 등)로 끝나도, 고객은 그 종료의 고정 문장 뒤에 같은 안내 문장을 받는다. 고정 문장은 상담원 연결이면 "상담원에게 연결해 드리겠습니다. 잠시만 기다려 주세요.", 컨텍스트 한도면 세션을 닫는 안내, 한도·예외면 "죄송합니다. 방금 요청을 끝까지 처리하지 못했습니다. 다시 한 번 말씀해 주시거나 상담원 연결을 요청해 주세요."다. 전에는 이런 턴에서 안내가 빠졌고, 한도·예외 종료에는 "방금 요청을 처리하지 못했습니다"만 갔다 (승인 대기는 그대로 올라가 있어 화면의 승인 칩만 단서였다). 대화 기록과 감사 로그의 답도 고객이 받은 글과 같고, 한도·예외 종료의 오류 기록과 `error` 이벤트는 그대로 남는다. 상담원 연결이나 컨텍스트 한도로 닫힌 세션에도 결정 결과는 이 대화창에 들어간다. `tests/test_service.py`가 네 종료를 대본으로 재생해 확인한다
    - **알려진 틈**: 지시를 다른 말로 바꿔 옮기면(예: "동일한 요청은 재시도하지 마세요"처럼 10자 이상 이어서 같은 글자가 없는 말) 걸러지지 않고 고객에게 간다. 남는 모델의 말이 승인 대기와 맞는지는 따로 보지 않는다 (모델이 "취소되었습니다"라고 하면 그 뒤에 "아직 처리되지 않았습니다" 안내가 붙어 고객은 두 말을 함께 읽는다. 완료 주장 가드 `CLAIMS=C1`을 켜면 이런 답은 고객에게 가기 전에 다시 시킨다)
    - 처음 고친 `972317b`는 다른 쓰기가 성공한 턴에만 모델 답을 남겼다. 그래서 조회와 질문만 있던 턴(본인 확인 → 주문 조회 → 취소가 승인에 걸림)은 조회 결과까지 모델 답 전체가 고객에게 가지 않았고, 버려진 답은 대화 기록에 남아 다음 턴의 모델이 고객에게 한 말로 읽었다. 같은 날 리뷰에서 찾아 지금처럼 고쳤다 (`tests/test_service.py`에 그 턴을 대본으로 재생하는 테스트와 지시를 옮긴 여러 표현의 테스트)
  - 이렇게 한 이유: 평가가 잰 것을 바꾸지 않기 위해서다. 승인 관문은 서비스에만 있고 평가에는 없다 (평가의 도구는 10만 원 이상 취소도 바로 실행한다). 에이전트 루프(`agent.py`)도, 모델이 받는 도구 결과 문구도 바이트까지 그대로라(테스트가 문구를 고정한다) 서비스의 모델이 받는 입력과 완료 주장 가드가 근거로 읽는 형식(`claims.py`)이 바뀌지 않는다. 바뀌는 것은 고객에게 보내는 글뿐이다. 모델에게 주는 문구에서 지시를 빼는 방법은 모델의 입력을 바꾸고, 그래도 모델이 다른 문장을 옮길 수 있다. 모델 답을 거르기만 하는 방법은 말을 바꾸면 빠져나가므로, 고객이 꼭 들어야 하는 것(주문, 금액, 승인 번호, 결과를 이 대화창으로 알린다는 것)은 모델 답과 상관없이 정해진 문장으로 붙인다. 모델 답을 통째로 버리면 같은 턴의 조회 결과와 질문이 사라지므로(위 `972317b`) 거른 모델 답을 그 앞에 둔다
  - 승인은 조건부 UPDATE 한 번으로 선점한다(`pending` → `executing`). 두 담당자가, 또는 두 프로세스가 같은 승인을 동시에 눌러도 한쪽만 실행한다. 실행 중에 오류가 나면(감사 행을 쓰지 못함, DB 오류 등) 도구의 변경은 롤백되고 승인은 `pending`으로 돌아가 다시 결정할 수 있다 (관리 화면에는 "결정을 저장하지 못했습니다"가 뜨고 감사 로그에 오류가 남는다). 실행 중에 프로세스가 죽거나, 되돌릴 때 DB에 닿지 못하면 `executing`으로 남는다. 이때 쇼핑몰 데이터는 바뀌지 않았으므로(아래) 사람이 확인하고 다시 요청하면 된다
- **쇼핑몰 데이터의 변경과 감사 로그는 한 트랜잭션이다.** 도구가 성공하면 그 호출의 감사 행과, 승인 실행이면 승인의 `approved` 표시까지 도구의 변경과 함께 커밋되거나 함께 롤백된다 (`toolkit.execute`의 `on_success`). 감사 행 없이 주문만 바뀐 상태는 생기지 않는다. 대화 기록은 턴이 끝날 때 따로 저장하므로, 턴 도중 프로세스가 죽으면 대화에는 그 호출이 없고 감사 로그에는 있다. 고객이 다시 요청하면 도구가 이미 처리된 주문이라고 거절한다
  - 결과는 정해진 문장으로 대화에 들어간다 (모델이 쓰지 않는다). 고객 화면은 5초마다 대화를 다시 읽어 보여 준다.
- **감사 로그는 추가만 한다.** 고객 메시지, LLM 호출(토큰 수·시간·형식 오류), 도구 호출(인자, 결과, 쓰기 여부, 본인 확인된 고객), 응답, 승인 요청과 결정이 한 줄씩 남는다. 거절된 도구 호출은 바뀐 것이 없으므로 따로 적는다.
- **세션 id가 곧 열쇠다.** 고객 쪽에는 로그인이 없다. 본인 확인은 평가와 같이 `find_customer`(이름 + 연락처)로 하고, 확인된 고객 번호는 세션에 저장된다. 세션 id는 추측할 수 없는 난수다. 이 id가 요청 경로에 들어가므로(`/api/sessions/{id}/…`) 접근 로그와 앞단 프록시의 로그에 남기지 않는다: Docker 이미지와 위 실행 명령은 uvicorn 접근 로그를 끈다(`--no-access-log`, 2026-10-30부터. 그 전에는 켜져 있어 요청마다 경로가 로그에 남았다). 앞에 프록시를 두면 그 접근 로그에서도 경로를 빼거나 가린다. 상담에서 일어난 일은 감사 로그에 남고, 서버의 시작·경고·오류 로그는 그대로 나온다.
- **`Host` 헤더는 허용 목록으로 거른다 (2026-11-24부터).** 이 서비스는 로그인 없는 고객 API와 공유 토큰 하나뿐인 관리자 API를 127.0.0.1에만 열어 쓰는데, DNS 리바인딩이 그 전제를 피해 간다: 운영자가 서비스를 띄운 채 공격자 페이지(`http://attacker.example:8062`)를 열면 공격자의 DNS가 그 이름을 127.0.0.1로 다시 풀고, 페이지의 `fetch`는 같은 출처 요청으로 이 포트에 닿는다. 같은 출처라 CORS 사전 요청이 없고 `X-Admin-Token`도 붙일 수 있으며, 서버에는 `Host: attacker.example:8062`로 도착한다. 그 꼴의 요청(Host·Origin이 공격자의 이름, compose의 기본 토큰)을 TestClient로 보내 확인했다: 세션 만들기, 본인 확인, 큰 취소의 승인 대기, 관리자의 승인 목록·감사 로그 읽기, 승인 실행이 모두 통과했다. 그래서 `create_app`이 Starlette `TrustedHostMiddleware`로 `Host`를 걸러, 목록 밖이면 화면·정적 파일·API·없는 경로 어디든 경로와 본문을 보기 전에 400(`Invalid host header`)을 돌려준다. 거절 응답에도 보안 헤더가 붙는다(Host 검사를 보안 헤더 미들웨어 안쪽에 두었다). 모델 없는 오프라인 앱도 같은 `create_app`이라 같다. 이 저장소의 stt-scratch 서비스도 같은 방어를 쓴다.
  - 기본 허용은 `127.0.0.1`과 `localhost`이고 포트는 보지 않는다(8062, 컨테이너 안 8000, 시연용 18062 모두). 이름을 더하려면 `SUPPORT_AGENT_ALLOWED_HOSTS`(Compose는 `.env`의 `ALLOWED_HOSTS`)에 쉼표로 적는다. 이름과 IPv4 주소만 받는다: 와일드카드(`*`는 검사를 통째로 끈다)와 하위 도메인 패턴, 포트, `http://`, 경로, IPv6 주소, 빈 항목은 서비스가 시작할 때 거절한다. 시험은 `tests/test_host_allow_list.py`
  - IPv6 주소 표기(`http://[::1]:8062`)는 받지 않는다. 잠금의 Starlette 1.6.0은 `Host`에서 첫 `:` 앞만 읽어 `[::1]`이 어떤 목록 항목과도 같을 수 없다(이 저장소의 stt-scratch가 쓰는 Starlette 1.7.0은 괄호를 보존해 읽어 `[::1]`이 맞는다). 그래서 `[::1]`은 기본 목록에 넣지 않았다. `localhost`는 IPv6 루프백으로도 풀리므로 그 이름으로 접속하면 된다
  - `127.0.0.1`이나 `localhost`로 부르는 것은 그대로 된다: 컨테이너 안 HEALTHCHECK(`127.0.0.1:8000`), compose가 여는 포트(127.0.0.1에만 묶임), 보안 스캔 도구의 기본 대상(`http://127.0.0.1:8062`). `tests/test_deploy_config.py`가 이 주소들이 기본 목록 안에 있는지 확인한다. MCP 서버는 이 앱을 쓰지 않는다(HTTP 모드는 자기 SDK가 localhost 주소의 DNS 리바인딩을 막는다). ZAP이 `Host`를 바꿔 보내는 요청(클라우드 메타데이터 규칙 등)은 이제 404가 아니라 400을 받을 수 있다. `Host`는 적힌 글자 그대로 견준다(잠금의 Starlette 1.6.0): `LOCALHOST:8062`처럼 대문자로 쓰거나 끝에 점을 붙인 이름(`localhost.`)은 목록 밖으로 보아 400이다. 브라우저는 주소의 호스트 이름을 소문자로 바꿔 보내므로 화면에서는 차이가 없다
  - compose의 기본 관리자 토큰(`local-admin`)은 로컬 시연용으로 받아들인 값이라 그대로 둔다. 브라우저를 거쳐 그 토큰으로 관리자 API에 닿는 길은 이 방어로 닫혔다: 다른 사이트의 페이지는 사용자 정의 헤더 때문에 CORS 사전 요청에서 막히고, 이름을 위장한 페이지는 `Host` 검사에서 막힌다
- **고정 시계.** 생성 데이터는 2026-09-14 10:00(KST) 무렵에 맞춰져 있다. 실제 시계를 쓰면 곧 모든 주문이 반품 기간을 넘기므로 시연은 이 시각에 고정한다. `SUPPORT_AGENT_NOW=real`이면 실제 시계를 쓴다. 고정되는 것은 도구와 규정이 보는 "쇼핑몰의 지금"뿐이고, 세션·감사 로그·승인 기록의 시각은 항상 실제 시각이다.
- **한 세션은 한 번에 메시지 하나.** 프로세스 안의 세션별 잠금으로 막는다. 그래서 앱은 프로세스 하나로 띄운다. 여러 프로세스로 늘리려면 이 잠금을 DB 행 잠금으로 바꿔야 한다. 승인 결정과 MCP 호출도 같은 잠금을 거치며 30초까지 기다린다 (채팅 메시지는 기다리지 않고 "앞선 메시지에 답하는 중" 안내를 받는다). 2026-10-24부터 세션별 잠금은 그 세션의 요청이 잠금을 쥐거나 기다리는 동안에만 메모리에 두고, 마지막 요청이 끝나면 지운다. 전에는 한 번 만든 잠금을 지우지 않아, 닫힌 세션과 MCP 상담의 잠금까지 프로세스가 사는 동안 세션 수만큼 늘었다. 턴이 끝날 때 승인 결정이 그 잠금을 기다리고 있으면 지우지 않고 결정이 이어받으므로, 지워도 한 세션의 요청이 함께 도는 일은 없다 (`tests/test_service.py`가 겹치는 턴과 결정으로 확인한다). 같은 승인을 두 번 실행하지 않는 것은 이 잠금이 아니라 위 "사람 승인"의 조건부 UPDATE가 맡는다.
- **한도.** 메시지 1,000자(설정으로 4,000자까지), 턴당 LLM 호출 12번과 실패한 도구 호출 10번(넘으면 그 턴은 고정 안내로 끝난다. 앞 턴들의 실패는 세지 않는다), 세션당 40턴, 동시에 도는 턴 4개(넘으면 503과 `Retry-After`. 설정 `MAX_CONCURRENT_TURNS`, 2026-10-24부터 상한 16: 턴의 SSE 응답 생성기는 동기 함수라 Starlette가 이벤트를 하나 꺼낼 때마다 anyio 스레드 풀(기본 40자리)에서 돌리는데, 다음 이벤트를 기다리는 동안(모델이 답할 때까지) 그 자리를 쥔 채 멈춰 있다. 같은 풀을 `/healthz`·글 메시지 수신·대화 조회·관리자 API의 동기 처리기가 쓰므로, 이 값을 40 가까이 올리면 턴이 자리를 모두 차지해 `/healthz`가 답하지 못하고 Docker의 HEALTHCHECK가 실패해 재시작될 수 있다. 16이면 턴이 모두 차도 자리 24개가 남는다. 이벤트 큐를 asyncio로 바꿔 자리를 쓰지 않게 하는 수정은 하지 않았다), 음성 모드에서 답을 읽어 주는 합성(`/speech`) 2개(설정 `MAX_CONCURRENT_SPEECH`, 2026-10-24부터. 넘으면 기다리지 않고 429와 `Retry-After: 2`로 돌려보내고, 화면은 그 시간 뒤 한 번만 다시 청한다. 턴 자리와는 따로 센다. 전에는 `/speech`에 한도가 없었다: 음성 모델은 한 번에 하나만 돌리므로 겹친 요청이 모두 작업 스레드를 쥔 채 합성 잠금을 기다렸고, 세션 하나로 `/speech`를 수십 개 겹쳐 보내면 같은 스레드 풀을 쓰는 채팅·대화 조회·관리자 API까지 수 분 멈출 수 있었다). 컨텍스트가 차거나 40턴이 되면 세션을 닫고 새 상담을 권한다. 컨텍스트는 프롬프트가 `num_ctx`(16384)의 95%를 넘었을 때와, 2026-10-15부터는 한 번에 `num_ctx`를 넘은 요청을 Ollama가 거절했을 때(요청에 `truncate: false`를 넣는다)다. 전에는 넘친 요청을 Ollama가 앞부분(시스템 프롬프트의 규정 포함)을 조용히 잘라 답했다. 음성은 파일 5 MB와 풀었을 때 60초까지이고 (길이는 푸는 도중에 프레임마다, 16 kHz로 바꾸기 전에 센다. 몇 kB짜리 파일에 몇 시간의 무음이 들 수 있고 샘플레이트가 아주 낮으면 프레임 하나가 몇 시간이 되어서, 다 푼 뒤나 16 kHz로 바꾼 뒤에 재면 그 사이 메모리를 수백 MB~GB 쓴다), 인식된 문장이 메시지 한도를 넘으면 자르지 않고 다시 말해 달라고 한다 (문장 끝의 "취소하지 마세요"가 잘리면 뜻이 뒤집힌다).
  - **설정 범위 (2026-10-24부터).** 정수 설정은 서비스가 시작할 때 범위를 검사하고, 벗어나면 `ValidationError`로 뜨지 않는다: `MAX_AGENT_CALLS_PER_TURN`·`MAX_TURNS_PER_SESSION`·`MAX_AUDIO_BYTES`·`MAX_AUDIO_SECONDS`·`MAX_CONCURRENT_TURNS`·`MAX_CONCURRENT_SPEECH`는 1 이상(`MAX_CONCURRENT_TURNS`는 16 이하, 위), `MAX_MESSAGE_CHARS`·`MAX_TTS_CHARS`는 1~4,000, `NUM_CTX`는 4,096 이상(시스템 프롬프트와 도구 설명만으로 첫 에이전트 호출의 프롬프트가 약 3,500토큰이라 그보다 작으면 모든 상담이 첫 턴에 컨텍스트 한도로 닫힌다), `APPROVAL_REFUND_WON`은 0 이상(0이면 취소·반품이 환불액과 상관없이 모두 승인 대기). 세션당 턴 수에는 상한이 없다 (보안 스캔은 100000으로 띄운다). 전에는 글자 한도 둘만 검사해, 예컨대 `MAX_TURNS_PER_SESSION=0`이면 모든 세션이 첫 메시지 뒤 닫히고 `MAX_CONCURRENT_TURNS=0`이면 모든 메시지가 503인데 `/healthz`는 정상이라 설정이 원인이라는 신호가 없었다 (`tests/test_review_t7.py`)
  - **요청 검증 오류는 입력을 되돌려 보내지 않는다 (2026-10-24부터).** 요청 본문이 모델(`MessageIn`·`SpeakIn`·`DecisionIn`)에 맞지 않으면 422와 함께 어느 칸이 왜 틀렸는지(`loc`·`msg`·`type`)만 돌려주고, FastAPI 기본 응답에 있던 입력 원문(`input`)은 뺀다. 전에는 짝 없는 서로게이트(JSON 이스케이프 `\ud800`)가 든 본문에서 pydantic이 거절한 뒤 기본 응답이 그 원문을 UTF-8로 인코딩하다 실패해 500과 트레이스백이 남았다 (글 메시지·`/speech`·관리자 결정 본문 모두. ZAP 8~11차는 이런 입력을 보내지 않아 '5xx 0건'에 잡히지 않았다). MCP 서버도 인자에 이런 글이 있으면 세션과 감사 행을 만들기 전에 `invalid_arguments`로 거절한다 (전에는 인자 크기 검사의 인코딩에서 예외가 나 SDK의 일반 오류가 돌아갔다. `tests/test_mcp_server.py`)
  - **세션 번호에 NUL(`%00`)이 든 요청은 없는 세션(404)이다 (2026-11-24부터).** 요청 경로의 `%00`은 디코딩되어 NUL 문자(0x00)로 처리기에 온다. PostgreSQL의 text 값에는 NUL을 넣을 수 없어서 PostgreSQL 드라이버(psycopg 3)는 그런 문자열을 쿼리 인자로 쓰려는 순간(서버로 보내기 전) `DataError`를 냈고, 웹 계층이 그 예외를 잡지 않아 로그인 전의 누구나 요청 하나로 500과 트레이스백을 낼 수 있었다(고객의 대화 조회·글 메시지·음성 메시지·답 읽어 주기, 관리자의 대화 조회 모두). 이제 세션을 확인하는 서비스 메서드(`service/core.py`의 `_row`, `session_status`)가 NUL이 든 번호를 DB에 묻기 전에 없는 세션으로 돌려준다. 서비스가 만드는 번호는 `token_urlsafe`라 NUL이 들어 있을 수 없으므로 '없는 세션은 404'라는 계약은 그대로다. SQLite는 NUL이 든 인자도 받아 늘 404였기 때문에, 보안 스캔(모두 SQLite 오프라인 앱)과 SQLite 위의 시험에는 잡히지 않았다. 시험은 `tests/test_session_id_nul.py`(PostgreSQL 없이, 드라이버처럼 NUL을 거절하는 SQLite 엔진)와 `tests/test_postgres.py`(실제 PostgreSQL)다

## 상담 후처리 기록 (2026-11-25 추가)

관리자는 상담 하나의 대화를 상담 후처리 서비스(이 저장소의 call-summary)로 보내 상담 후처리 기록(문의 유형, 처리 결과, 핵심 값, 처리한 일, 후속 조치, 요약)을 만들 수 있다. 기본은 꺼져 있고, 관리자가 부를 때만 만든다.

- **켜는 법.** `SUPPORT_AGENT_SUMMARY_URL`에 후처리 서비스의 주소를 준다(`http://` 또는 `https://`와 호스트 이름이나 IPv4 주소. 포트와 경로는 붙여도 되고 끝의 `/`는 뗀다. 사용자 정보·질의·조각·IPv6 주소가 든 값은 서비스가 시작할 때 거절한다). 요청 하나를 기다리는 시간 상한은 `SUPPORT_AGENT_SUMMARY_TIMEOUT_S`(초, 1\~600, 기본 120)다. Compose는 `.env`의 `SUMMARY_URL`·`SUMMARY_TIMEOUT_S`이고, 그 주소는 앱 컨테이너 안에서 본 주소다(컨테이너 안의 `127.0.0.1`은 앱 컨테이너 자신이다). 켜졌는지는 `/healthz`의 `summary`(`true`/`false`)로 본다. 그 서비스가 지금 답하는지는 보지 않는다. 모델 없이 써 보려면 call-summary의 모델 없는 앱(`call_summary.service:create_offline_app`, 업종만으로 정해지는 고정 기록을 답한다)을 띄우고 그 주소를 준다
- **끝점.** `POST /api/admin/sessions/{session_id}/summary`(관리자 토큰 `X-Admin-Token`), 본문 `{"by": "담당자 이름"}`(1\~64자, `{}`면 `admin`). 서비스는 고객에게 보인 대화(`GET /api/sessions/{id}`의 `messages`. 첫 줄의 상담원 인사말을 포함하고, 도구 결과와 전달하지 않은 답은 빠진다)를 `{"domain": "shop", "turns": [{"speaker": "고객" 또는 "상담원", "text": 글}, …]}`로 바꿔 후처리 서비스의 `POST /summarize`에 한 번 보낸다(다시 보내지 않는다). 글은 고치지 않고 그대로 보낸다
- **응답.** 201 `{"session_id": …, "summary": {"record": …, "needs_confirmation": […], "model": …, "attempts": …}}`. `record`와 `needs_confirmation`(다시 확인할 번호)은 후처리 서비스가 준 그대로다
- **상태 코드.** 검사 차례는 관리자 토큰(401, 토큰을 설정하지 않은 서버는 503) → 연결이 꺼짐(501) → 본문(422) → 자리(429) → 세션(404·409) → 후처리 서비스다. 본문이 JSON 문법부터 틀린 요청만은 FastAPI가 토큰 검사보다 먼저 422로 끝낸다(다른 본문 끝점과 같다)
  - 501 `the summary link is disabled (SUPPORT_AGENT_SUMMARY_URL is not set)`: 연결이 꺼져 있다. 꺼져 있으면 세션이 있는지도 보지 않는다(꺼진 기능이 세션의 있고 없음을 알려 주지 않게). 503이 아닌 까닭: 관리 화면은 503을 '관리자 기능이 꺼짐'으로 읽어 로그인 화면을 띄우므로, 서버를 주소 없이 다시 띄운 뒤 열려 있던 화면에서 불러도 로그인이 풀리지 않게 했다
  - 404 없는 세션, 409 대화가 비어 있음(`this session has no conversation to summarize`. MCP 상담은 대화가 없다)
  - 422 본문이 틀림(입력 원문은 되돌려 보내지 않는다. 위 "정한 것과 이유"의 '요청 검증 오류는 입력을 되돌려 보내지 않는다'와 같은 처리기가 이 본문 모델 `SummaryIn`에도 걸린다), 후처리 서비스가 그 대화를 받지 않음(`the summary service rejected this conversation (422)`, 그쪽이 413이면 `(413)`), 보낼 본문이 64 KiB를 넘음(`the conversation is too long for the summary service`. 보내지 않는다)
  - 429와 `Retry-After`: 동시에 만드는 요청이 이미 둘이다(기다리지 않고 바로 돌려보낸다, `Retry-After: 10`), 또는 후처리 서비스가 붐빈다(그쪽 503. `Retry-After`는 그쪽 값이 1\~3600의 정수일 때만 그 값, 아니면 30). 503이 아닌 까닭은 위 501과 같다
  - 502 후처리 서비스에 닿지 못함(`the summary service is unreachable`), 그쪽이 200이 아닌 상태로 답함(`the summary service answered <코드>`. 넘겨 주기 3xx는 따라가지 않는다), 쓸 수 없는 답(`the summary service sent an unexpected reply`: JSON 객체가 아님, 압축함, 1 MiB를 넘음, 아래 "답의 확인"에 걸림)
  - 504 시간 초과(`the summary service timed out`)
  - 오류 글은 고정 문장과 상태 코드뿐이다. 후처리 서비스가 준 본문의 글(그쪽의 422 본문에는 문제가 된 입력 원문, 곧 고객의 글이 들어 있다), 대화의 글, 주소는 넣지 않는다
- **감사 로그.** 성공하면 `summary_created`(`by`, `session_status`(읽은 때의 세션 상태), `turns`(보낸 발화 수), `record`, `needs_confirmation`, `model`, `attempts`, `request_id`), 실패하면 `summary_failed`(`by`, `status`, `error`. `error`는 위의 고정 문장)가 한 행씩 남는다. 관리자가 해 봤는데 안 된 것도 감사 표에서 보이게 실패도 적는다. 자리가 없어 바로 돌려보낸 429와, 토큰·꺼짐·본문·없는 세션에서 끝난 요청은 남지 않는다. `record`는 후처리 서비스가 대화로 만든 기록이라 대화에서 나온 값(요약 글, 주문 번호 같은 핵심 값)이 들어 있다
- **대화와 턴은 건드리지 않는다.** 기록을 만드는 일은 대화를 읽기만 하고(대화 상태, 턴 수, 세션 상태를 쓰지 않는다) 상담 턴의 경로(평가와 같은 에이전트 루프와 도구)를 지나지 않는다. 후처리 서비스를 기다리는 동안 세션 잠금과 DB 세션을 쥐지 않으므로 그동안에도 고객은 같은 세션에서 상담할 수 있고, 기록은 읽은 때의 대화로 만든다. 후처리 서비스가 실패해도 상담은 그대로다
- **자리.** 동시에 만드는 기록은 둘까지다. 관리자 API 처리기는 스레드 풀(기본 40자리)에서 돌고 후처리 요청 하나가 그쪽이 답할 때까지 자리 하나를 쥐므로, 한도가 없으면 겹친 요청이 같은 풀을 쓰는 `/healthz`와 다른 관리자 API를 멈출 수 있다(위 "한도"의 답 읽어 주기와 같은 까닭). 자리는 어느 길로 끝나도 돌려준다
- **연결.** 주소는 설정에서만 받는다(요청으로 받으면 관리자 토큰으로 서비스를 시켜 서비스만 닿는 내부 주소로 대화를 보내게 할 수 있다). 넘겨 주기(3xx)를 따라가지 않고, 프록시 환경 변수(`HTTP_PROXY` 등)를 읽지 않으며, 인증 머리를 싣지 않고, 쉬는 연결을 남기지 않는다(요청마다 새 연결. 쉬던 연결을 다시 쓰는 순간 그쪽이 닫아 드물게 생기는 502를 막는다). 응답은 흘려 받으며 1 MiB를 넘는 순간 끊고, 압축한 답은 읽지 않는다(압축을 풀면 크기 한도가 메모리를 지키지 못한다). 까닭은 `service/summary.py`의 머리 주석에 있다
- **답의 확인.** 후처리 서비스의 답은 믿지 않는다. 받은 답에서 다섯 칸(`record`, `needs_confirmation`, `model`, `attempts`, `request_id`)을 꺼내기 전에 꼴을 확인한다. (1) 다섯 칸이 모두 있고 형이 맞아야 한다: `record`는 객체, `needs_confirmation`은 목록, `model`과 `request_id`는 글, `attempts`는 정수(`true`·`false`는 정수가 아니다). (2) 겹침이 32단 이하여야 한다(다섯 칸을 담은 객체를 1단으로 센다. 정상 답은 4단 안쪽이다). (3) JSON으로 다시 쓸 수 있어야 한다: `NaN`·`Infinity`(너무 커서 무한대로 읽히는 수 포함)와 짝 없는 서로게이트가 값에도 객체의 키에도 없어야 한다. NUL 문자가 든 글은 거절하지 않는다. 하나라도 어긋나면 502(`the summary service sent an unexpected reply`)이고 감사 로그에는 `summary_failed`만 남는다. 확인하지 않으면 그런 답이 `summary_created`로 저장되는데, 감사 로그는 추가만 하고 지우는 길이 없고 응답을 내보내는 직렬화는 그런 값(짝 없는 서로게이트, 100단 가까이 겹친 값)에서 실패하므로 그 세션의 관리자 대화 조회가 계속 500이 된다. 칸의 내용은 해석하지 않고 그대로 감사 로그에 남긴다. 관리 화면은 그것을 글로만 그린다(감사 표에는 `JSON.stringify`한 글을 `textContent`로 넣는다)
- **한계.**
  - 고객에게 보인 대화의 글이 설정한 주소로 그대로 나간다. 그 주소는 운영자가 믿는 서비스여야 한다
  - `http://` 주소는 암호화하지 않는다. 같은 호스트나 같은 컨테이너 망 밖의 서비스를 `http://`로 부르면 대화의 글(이름, 연락처, 주문 번호가 들 수 있다)이 암호화 없이 나가고 받는 답도 중간에서 바뀔 수 있다. 그런 곳에는 `https://` 주소를 쓴다
  - 환경 변수의 프록시·인증서 설정(`HTTP_PROXY`, `SSL_CERT_FILE` 등)을 읽지 않는다(`httpx.Client`를 `trust_env=False`로 만든다). 그래서 사설 인증 기관이 낸 인증서를 쓰는 `https://` 주소는 인증서를 확인하지 못해 연결되지 않는다(502 `the summary service is unreachable`). 인증서는 httpx가 쓰는 인증 기관 묶음(`certifi`)으로만 확인한다
  - 후처리 서비스에는 인증이 없다(call-summary는 포트를 루프백에만 연다). 이 연결도 인증 머리를 싣지 않는다
  - 업종은 `shop`으로 고정이다(이 서비스는 가상 쇼핑몰의 고객센터다)
  - 자동으로 만들지 않는다. 관리자가 부를 때만 만들고, 만든 기록은 응답과 감사 로그에만 남는다(따로 저장하거나 고객에게 보내지 않는다)
  - 후처리 서비스의 한도(발화 200개, 이어 붙인 전사 4,000자, 요청 본문 64 KiB)를 넘는 상담은 422로 끝난다. 기본 세션 한도(40턴)면 발화 수는 넘지 않지만, 메시지가 길면 4,000자와 64 KiB는 넘을 수 있다
  - 시간 상한(`SUMMARY_TIMEOUT_S`)은 연결과 읽기 한 번(응답 머리나 본문 조각 하나를 기다리는 사이)마다 걸린다. 본문을 받는 동안과 다 받은 뒤에는 요청을 시작한 때부터 잰 전체 시간으로도 끊는다(상한을 넘겨 끝난 답은 쓰지 않고 504). 다만 응답 머리를 받는 동안(1xx 임시 응답이 이어지는 동안 포함)에는 전체 시간 상한이 없고 읽기 제한만 걸린다. 머리를 조금씩 계속 보내는 서버는 상한보다 훨씬 오래 요청 하나를 붙잡을 수 있다. 그 피해는 위 "자리" 둘에 갇힌다: 둘이 모두 묶여도 후처리 기록 만들기만 429이고 다른 경로는 그대로다
  - 답은 1 MiB까지 받는다. 그만큼이 감사 로그의 한 행에 남을 수 있다(한글은 JSON으로 저장될 때 이스케이프되어 저장 크기가 두 배쯤 된다. 0.9 MB의 답이 SQLite에서 1.8 MB쯤의 행이 되는 것을 쟀다). 응답과 관리자 대화 조회도 그만큼 커진다. 정상 답은 기록 하나와 번호 확인 표시 몇 개라 이보다 훨씬 작다
  - 기본 시간 상한 120초는 후처리 서비스 쪽의 최악 대기(자리 대기 30초 + 모델 호출 한도 120초 × 두 번, 약 270초)보다 짧다. 그쪽이 오래 줄을 서거나 다시 시도하는 요청은 504가 될 수 있고, 그럴 때는 상한을 600초까지 올린다
- **시험.** `tests/test_summary_link.py`: 클라이언트는 가짜 서비스(`httpx.MockTransport`)로 실패 표, 답의 꼴(다섯 칸의 형, 겹침 깊이, 다시 쓸 수 없는 값), 크기·시간 한도, 넘겨 주기·프록시·쉬는 연결 설정을 보고, 끝점은 마이그레이션한 SQLite 파일과 대본대로 답하는 가짜 모델로 꺼짐, 검사 차례, 기록과 감사 로그, 실패, 쓸 수 없는 답을 저장하지 않음, 자리, 잠금과 DB 연결을 쥐지 않음을 본다. `tests/test_host_allow_list.py`는 목록 밖 `Host`의 요청이 이 끝점에서도 400인지 본다

## 음성

선택 기능이다. `SUPPORT_AGENT_VOICE=1`이면 마이크로 말하고 답을 소리로 들을 수 있다. 인식된 문장은 글로 보낸 메시지와 같은 길을 가므로 규정 검사, 사람 승인, 감사 로그가 그대로 적용된다. 설치와 끝점은 [voice.md](voice.md).

## qwen2.5 7B로 써 보면 (2026-10-04까지의 기본 모델)

2026-10-04까지의 기본 모델 qwen2.5 7B는 측정한 그대로 움직인다. 개발용 과제의 20%만 끝까지 처리하고, 가장 흔한 실패는 "확인해 보겠습니다"만 하고 도구를 부르지 않는 것이다. 실제 모델로 서비스를 확인할 때도 주문 취소를 세 번 부탁하는 동안 같은 말만 되풀이했고, 조회 도구를 부르지 않고 주문 상태를 지어내기도 했다. 가장 나쁜 경우도 나왔다: `docker compose`로 띄운 서비스에서 주문 취소를 부탁하자 7B는 취소 도구를 한 번도 부르지 않은 채 "주문이 취소되었습니다. 12,000원이 환불되었습니다"라고 답했다. 주문은 DB에 결제 완료 그대로였고, 12,000원은 규정 문서의 예시에 나오는 금액이다. 도구가 규정을 막고 큰 환불은 사람이 승인하므로 잘못된 처리가 DB에 남지는 않지만, 하지 않은 일을 했다고 말하는 것은 막지 못한다. 평가에서는 이런 에피소드가 실패로 잡힌다 (최종 DB가 정답과 다르다). 그래서 "끝났다"는 답을 그 대화의 도구 결과와 대조해 근거가 없으면 돌려보내는 가드를 만들어 쟀다 (`experiments.md` 7단계). 거짓 완료의 전달은 0이 되지만 7B는 안내문을 받고도 도구를 부르지 않아 성공률이 오르지 않았고(C1 −2.1%p, 정답에 없는 쓰기 한 건 증가), 재기 전에 적은 조건에 걸려 기본값으로 켜지 않았다. `SUPPORT_AGENT_CLAIMS=C1`로 켤 수 있고, 켜면 세 번째에도 같은 주장을 하는 턴에는 "방금 요청을 처리하지 못했습니다"라는 고정 안내가 나간다. 14B는 성공률이 두 배쯤이고(`MODEL=qwen2.5:14b-instruct`) 이 PC에서는 호출당 몇 초가 걸린다.

새 기본 모델 `qwen3.5:4b`로는 2026-10-04에 서비스를 호스트에서 띄워(새 SQLite DB, 고정 시계, 기본 설정 그대로: P1, `think: false`, `/healthz`가 `"model":"qwen3.5:4b","think":"off"`) 실제 모델로 상담 두 개를 해 봤다. Ollama 0.35.1, RTX 2080 Ti, 끝날 때 모델은 100% GPU였다. 측정이 아니라 동작 확인이고(대화 둘), 시간은 GPU가 쉬지 않을 때(데스크톱 앱이 사용률 약 25%, 메모리 약 1.0~1.4 GiB) 본 참고값이다. 모델 없이 확인한 것(서비스가 보내는 모든 에이전트 요청에 `"model": "qwen3.5:4b"`와 `"think": false`가 들어가고, 이전 모델을 고르면 `think`를 보내지 않음. `tests/test_service.py`)은 그대로다.
- 작은 취소(정예준, O-90005, 89,100원): 첫 메시지에 이름·전화번호·주문 번호·요청을 함께 보내자 `find_customer` → `list_orders`를 부르고 "취소하시겠습니까?"라고 물었다. "네, 진행해 주세요"에 `cancel_order`를 불러 DB의 주문이 `cancelled`, 결제가 환불 대기 89,100원이 됐고, 답의 금액과 환불 수단(간편결제)이 DB와 같았다. 다만 동의를 묻기 전에 환불액을 말하지 않았다 (규정 3은 대상과 환불액을 말하고 동의를 받으라고 한다)
- 큰 취소(강정우, O-10097, 108,200원): 본인 확인 뒤 주문을 조회하지 않고 "취소하시겠습니까?"를 먼저 물었고, "네"에 `get_order`로 조회해 금액(108,200원)과 환불 수단(계좌이체)을 말하고 다시 물었다. 두 번째 "네"에 `cancel_order`가 승인 관문에 걸려 승인 대기 AP-1이 생기고 주문은 그대로였다. 이때의 답은 도구가 에이전트에게 돌려준 안내문(`service/core.py`의 `approval_required` 문구)을 거의 그대로 고객에게 옮겼다: "…담당자 확인 후 처리되며 결과는 이 대화창으로 안내된다고 알려드리겠습니다. 같은 요청을 다시 호출하지 마세요." 승인 번호는 말하지 않았다. 한 번 본 것이라 얼마나 자주 그러는지는 모르고, 고치지 않았다. **2026-10-05 고침** (`972317b`): 이제 승인 대기에 걸린 턴에 고객이 읽는 답은 서비스의 정해진 문장(주문, 금액, 승인 번호)이고 모델의 답은 전달하지 않는다 (위 "사람 승인". 이 대화를 대본으로 다시 재생하는 테스트가 `tests/test_service.py`에 있다. 모델 없는 오프라인 앱으로도 HTTP를 거쳐 확인했다: 대역은 도구 결과를 그대로 답으로 옮기는데, 고객에게는 정해진 문장이 갔고 지시가 든 대역의 답은 감사 로그의 `not_delivered`에만 남았다 (8차 스캔 준비). 실제 모델로 다시 확인하지는 않았다). **같은 날 다시 고침**: 모델 답을 통째로 버리면 같은 턴의 조회 결과와 질문도 사라져서, 지시를 옮긴 부분만 빼고 정해진 문장을 뒤에 붙인다 (위 "사람 승인")
- 7B에서 본 멈춤("확인해 보겠습니다")과 도구 없이 끝났다고 말하는 답은 이 두 대화에서는 나오지 않았다. 에이전트 호출 11번 모두 형식 오류(언어 가드 포함) 0이고, 감사 로그에 호출마다 토큰(프롬프트 3,526~4,314)과 시간이 남았다. 첫 호출은 D: HDD에서 모델을 읽느라 55초, 그 뒤는 0.4~1.4초였다 (2026-10-30 추가: 띄운 직후의 이 적재를 시작할 때 미리 하려면 `SUPPORT_AGENT_PRELOAD=1`, 위 "실행")
- 하지 않은 것: Compose(PostgreSQL) 스택, 음성 모드, 승인 뒤의 대화, 여러 턴에 걸친 다른 업무(반품·교환 등)

## 하지 않은 것

- 요청 빈도 제한이 없다 (동시 실행 수만 막는다: 턴 4개, 2026-10-24부터는 답 읽어 주기 2개도). 포트를 127.0.0.1에만 여는 것으로 대신했다 (2026-11-24 보탬: 그 대신이 브라우저를 거치는 DNS 리바인딩 경로에는 맞지 않아, 서비스가 `Host` 헤더를 허용 목록으로 거른다. 위 "정한 것과 이유"의 'Host 헤더'). 밖에 내놓으려면 앞단에 프록시와 빈도 제한이 필요하다. 세션을 만드는 요청(`POST /api/sessions`)에도 인증과 개수 상한이 없어 세션마다 DB 행과 감사 행이 남으므로, 이것도 같은 앞단이 막아야 한다 (프로세스 안의 세션별 잠금은 2026-10-24부터 요청이 끝나면 지우므로 세션 수만큼 늘지 않는다)
- 요청 본문의 크기 상한은 `/voice`의 5 MB(`MAX_AUDIO_BYTES`, 넘는 순간 413)뿐이다. JSON 끝점은 본문을 끝까지 읽은 뒤에 형식과 길이를 검사하므로 아주 큰 본문도 일단 메모리에 올라오고, `/voice`도 턴 자리를 잡기 전에 본문을 다 받는다 (자리를 먼저 잡으면 느린 업로드가 턴 자리를 쥐어 글 채팅까지 막으므로 순서를 바꾸지 않았다). 밖에 내놓으려면 앞단 프록시에서 본문 크기를 제한한다 (2026-10-24 추가)
- ~~같은 주문을 두 세션이 같은 순간에 바꾸는 경우는 DB 제약에 맡겼다~~ → **2026-10-15 고침**: 쓰기 도구가 주문 행을 `SELECT … FOR UPDATE`로 잠그고(쿠폰은 그다음 고객 행도, 티켓은 고객 행만. 잠금 순서는 늘 주문 → 고객), 교환의 재고는 "재고가 수량 이상일 때만 수량만큼 뺀다"는 조건부 UPDATE 한 번으로 줄인다. 그래서 같은 주문의 겹치는 줄을 두 세션이 같은 순간에 반품하면 늦은 쪽이 `already_requested`로 거절되고(전에는 접수 번호가 달라 둘 다 통과), 같은 옵션을 같은 순간에 교환해도 재고 차감이 사라지지 않으며(전에는 둘 다 같은 재고를 읽어 하나가 사라짐), 한 고객의 다른 주문 두 개에 같은 순간 쿠폰을 내도 30일 2장 한도를 넘지 않고, 같은 고객의 티켓 번호가 겹치지 않는다. 같은 주문의 반품 합계(승인 기준)도 늦은 쪽이 앞쪽의 접수를 본 뒤 센다. `tests/test_postgres.py`가 두 트랜잭션으로 다섯 경우를 확인한다(고치기 전 코드에서는 다섯 모두 실패). 평가(메모리 SQLite)는 SQLAlchemy가 SQLite에 `FOR UPDATE`를 보내지 않아 그대로다: 커밋된 기록의 도구 호출 12,974개를 고친 코드로 다시 실행하면 결과 글과 끝난 DB가 모두 기록과 같다(`tests/test_concurrency.py`가 일부를 CI에서 다시 돈다). 남은 것: 이관 번호(`HO-n`)는 전체 개수로 만들어 두 세션이 같은 순간에 이관하면 늦은 쪽이 기본 키 충돌로 실패한다(잠글 행 하나가 없다)
- Docker 없이 SQLite 파일로 띄운 서비스(위 "실행")는 한 사람이 써 보는 시연용이다. 바로 위의 행 잠금은 SQLite에서는 걸리지 않으므로(SQLAlchemy가 SQLite에 `FOR UPDATE`를 보내지 않는다), 행 잠금에 기대는 동시 쓰기 보호(겹치는 반품의 거절, 쿠폰 한도, 티켓 번호, 반품 합계)는 PostgreSQL(Compose)에서만 확인했다 (`tests/test_postgres.py`). SQLite에서는 확인하지 않았다. 여러 사람이 함께 쓰려면 Compose로 띄운다 (2026-10-29 추가)
- 턴 전체의 제한 시간이 없다. 모델 호출 하나의 제한 시간(10분)과 턴당 호출 수만 있다
- 완료 주장 가드를 켠 경우, 같은 턴에 쓰기가 성공한 뒤 다른 종류의 일을 끝냈다고 세 번 말하면 고객은 "처리하지 못했습니다"를 듣는다 (DB는 바뀌어 있다). 검출은 정규식이라 목록에 없는 표현("성공했습니다", 관형형 "발급된")은 빠져나간다
- 관리자 인증은 공유 토큰 하나다. 담당자 이름은 입력한 대로 기록된다
- 상담원 연결(`transfer_to_human`) 뒤를 받는 화면은 없다. 세션이 `handoff`로 닫히고 관리 화면의 상담 기록에 남는다
