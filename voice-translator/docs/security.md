# 보안 점검 기록

이 서비스는 한 PC에서 돌리는 것을 기본으로 한다(DB는 127.0.0.1에만 열리고, 화면·API는 `WEB_HOST_PORT`의 HTTP). 이 문서는 무엇을 확인했고 무엇을 받아들인 위험으로 남겼는지 적는다. 날짜가 붙은 항목은 그날의 결과이며 이후 바뀐 것은 덧붙여 적는다.

## 재현성 고정 (2026-10-15)

같은 파일로 다시 만들었을 때 같은 서버가 뜨도록, 받아 오는 것들을 판 번호나 해시로 고정했다.

2026-10-29 정정: 위 문장이 맞는 범위는 그날 표에 적은 다섯 행(음성 인식 모델, Docker 기본 이미지, 브라우저 말소리 판정 런타임, Python 의존성, npm 의존성)과 표 밖의 비교용 설정 Supertonic 3(리비전과 파일별 SHA-256, `backend/app/services/supertonic.py`)이었다. 서비스가 Hugging Face에서 받는 음성 합성·전처리 모델 — MeloTTS-Korean의 설정·체크포인트, MeloTTS 언어 모듈이 import 때 받는 BERT 토크나이저 6개와 첫 한국어 합성 때 받는 BERT 모델 kykim/bert-kor-base, Kokoro-82M의 설정·가중치·af_heart 목소리 — 는 2026-10-29 전까지 리비전 없이 허브의 `main`을 받고 있었다(고정한 MeloTTS 리비전의 `melo/download_utils.py`·`melo/text/*.py`와 kokoro 0.9.4의 `model.py`·`pipeline.py`가 `revision` 없이 받고, 이 저장소의 합성 코드(`backend/app/services/tts.py`)와 compose에도 이 모델들의 `revision`이나 `HF_HUB_OFFLINE`이 없었다). 그래서 상류 저장소가 바뀐 뒤에는 새로 클론해 빈 `hfcache` 볼륨으로 띄우는 서버뿐 아니라, 네트워크가 있는 채 기존 볼륨으로 다시 시작하는 서버도(huggingface_hub가 `main`이 지금 가리키는 커밋을 허브에 다시 묻는다) README의 수치를 낸 모델과 다른 파일을 조용히 읽을 수 있었다. 2026-10-29에 측정이 읽은 캐시의 커밋으로 고정했다(아래 표의 2026-10-29 행). 측정 수치는 바뀌지 않는다: 합성 후보 측정(docs/experiments.md 3절)의 측정 PC 캐시와 서비스 측정의 `hfcache` 볼륨 모두 저장소마다 스냅숏이 하나뿐이고, 고정한 커밋이 바로 그 스냅숏이다. 아직 고정하지 않은 것도 표 끝에 적었다.

## 의존성 취약점 (2026-10-15)

`pip-audit` 2.10.1(PyPI 권고 데이터베이스)과 `npm audit`으로 lock 그대로의 의존성을 검사했다. Python은 서버 환경(gpu + tts 그룹)과 측정 도구 환경(gpu + eval + dev 그룹)을 따로 내보내 검사했다(두 그룹은 함께 설치할 수 없다).

## 화면 서버(nginx)의 보안 머리글과 ZAP 기준 스캔 (2026-10-15)

`frontend/nginx.conf`에 보안 머리글·압축·캐시를 넣고, OWASP ZAP 기준 스캔(baseline: 수동 검사, 공격 요청 없음)을 바꾸기 전후로 한 번씩 돌렸다. 이 저장소에서 처음 한 동적 검사다.

**머리글** (모든 응답, 오류 포함. location이 캐시 머리글을 더해도 `add_header_inherit merge`로 함께 나간다 — nginx 1.29.3부터 있는 지시어, 배포 이미지는 1.30.6)

| 머리글 | 값 | 이유 |
|---|---|---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self'; media-src 'self' blob:; connect-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` | 화면의 스크립트·스타일·WASM·모델·워클릿은 모두 같은 출처의 빌드 파일이고, 실행 중에 외부로 나가지 않는다. `'wasm-unsafe-eval'`은 onnxruntime-web이 WebAssembly를 컴파일하는 데만 쓰인다(일반 eval은 막힌 채). `media-src blob:`은 번역 음성을 인증 요청으로 받아 blob URL로 재생하기 때문이다. 인라인 스크립트·스타일과 `data:` 스크립트를 허용하지 않아, XSS로 끼워 넣은 스크립트가 실행되기 어렵다 |
| `X-Frame-Options`, CSP `frame-ancestors 'none'` | `DENY` | 다른 사이트의 iframe에 넣지 못하게(클릭재킹) |
| `Permissions-Policy` | `microphone=(self)`, 그 밖의 장치·결제 기능 끔 | 마이크는 이 화면만 쓴다 |
| `X-Content-Type-Options` | `nosniff` | MIME 추측 실행 막기 |
| `Referrer-Policy` | `no-referrer` | 다른 곳으로 주소를 보내지 않음 |
| `Cross-Origin-Opener-Policy` / `-Resource-Policy` | `same-origin` | 다른 출처 창과 맥락을 나누고, 이 서버의 파일을 다른 출처 페이지가 끌어다 쓰지 못하게 |
| `Server` | `nginx`(판 번호 없음, `server_tokens off`) | 판 번호로 알려진 취약점을 고르기 어렵게 |

- **CSP에 맞춘 화면 수정**: 마이크 워클릿(`capture.worklet.js`, 2.5KB)을 Vite가 4KB 미만이라 `data:` URL로 묶어 넣고 있었다. CSP(`script-src 'self'`)는 `data:` 스크립트를 막으므로, 그대로였다면 배포 화면에서 대화 모드·동시통역·두 사람 대화의 마이크가 열리지 않았다. `?url&no-inline`으로 가져와 `/assets/capture.worklet-<해시>.js` 파일로 내보낸다(`frontend/src/conversation/microphone.ts`). 같은 CSP 아래에서 `data:` 워클릿을 올리면 막히는 것도 대조로 확인했다
- **압축과 캐시**: gzip(5단계)을 켰다. 대화 모드가 처음 받는 onnxruntime-web WASM 14.2MB가 3.72MB로 전송된다(재어 봄). Silero 모델(.onnx)은 86%까지만 줄어 압축하지 않는다. 이름에 내용 해시가 붙은 `/assets/` 파일은 1년 `immutable`로 캐시하고, 이름이 고정된 라이선스 원문 두 개와 `index.html`은 `no-cache`(매번 확인)다
- HSTS는 넣지 않았다: 기본 배포는 같은 PC의 HTTP다. HTTPS 앞단을 두는 쪽에서 정한다
- `Cross-Origin-Embedder-Policy`는 넣지 않았다: 브라우저 추론이 스레드 하나(`env.wasm.numThreads = 1`)라 교차 출처 격리가 필요 없고, 다른 출처 자원도 쓰지 않는다. 넣으면 앞으로 다른 출처 자원을 하나라도 쓸 때 조용히 막힌다

## 받아들인 위험: 가입 응답으로 계정 존재가 드러남 (2026-10-24 확인, 사용자 결정 대기)

- **2026-11-05 덧붙임**: 위 줄 끝의 확인(GPU로 서비스 전체를 띄워 음성 번역 한 건을 저장·재생)은 2026-11-01에 이 변경이 들어간 서버 이미지(2026-10-30의 잠금으로 빌드)로 했다. compose로 DB·교정 모델·API·화면을 GPU와 함께 띄우고(`CORRECTION_DIGEST`를 준 상태), 상태 확인의 모델 넷·`models_ok`·연속 실패 0과 교정 모델 준비를 본 뒤, 시험 계정으로 가입·로그인 → 글자 번역(영→한)과 그 번역 음성 받기 → 그 음성을 올린 음성 번역(한→영)과 번역 음성 받기 → 기록 2건 → 두 기록 지우기(204)와 지운 기록의 음성 404까지 확인 18개가 모두 통과했다. 컨테이너 안 `id -u`는 10001이고 두 볼륨은 10001 소유였다. - **남는 위험**: 서비스가 써야 하므로 이 사용자도 hfcache의 모델 파일과 다른 사용자의 번역 음성 파일을 바꾸거나 지울 수 있다. hfcache에서 서비스 코드가 직접 받는 합성 파일 5개는 시작할 때마다 SHA-256을 대조하지만(위 재현성 표), 음성 인식 모델과 BERT 토크나이저·모델은 리비전으로만 고정돼 있어 볼륨 안에서 바뀐 파일은 알아채지 못한다. API 컨테이너는 호스트에 포트를 열지 않고 화면(nginx) 뒤에만 있다

## 큰 요청 하나로 서버를 붙잡는 길의 상한 (2026-11-24)

API 서버는 작업자 하나(이벤트 루프 하나, 모델 스레드 하나)로 돈다. 요청 하나가 이벤트 루프나 모델 스레드를 오래 붙잡으면 그동안 모든 사용자의 HTTP 요청, 동시통역 자막, 번역이 함께 멈춘다. 로그인 없이(셋째는 가입만 하면) 보낼 수 있는 큰 요청 하나로 그렇게 되던 길 셋에 상한을 두었다. 시간은 모두 이 PC에서 서비스·포트·DB 없이 같은 프로세스 안에서 잰 것이다(HTTP는 httpx의 ASGI 전송과 같은 이벤트 루프의 10ms 시계로 잰 최장 정지, 웹소켓은 uvicorn이 쓰는 websockets 17.1 sans-io 프로토콜, 음성은 잠금과 같은 PyAV 18.1.0·faster-whisper 1.2.1).

**1. 검증 오류(422)와 요청 본문**

- 전: nginx의 본문 한도 `11m`가 모든 `/api/`에 걸렸고, FastAPI 기본 422 처리기는 오류 항목마다 보낸 값(`input`)을 담아 원소마다 다시 만들어 돌려줬다. 가입·토큰 갱신에 11MB JSON 목록(`[0,0,…]`)을 보내면 응답이 11,534,480바이트였고 이벤트 루프가 7.0초(갱신)·7.5초(가입) 멈췄다
- 바꾼 것: 앱의 422 처리기가 항목마다 위치(`loc`)·이유(`msg`)·종류(`type`)만 돌려준다(`backend/app/main.py`. 화면은 422 본문의 값을 쓰지 않고 상태 코드로 고정 문구를 고르며, docs/api.md '오류 응답'의 계약 문장을 이에 맞췄다). nginx의 본문 한도는 server 단계 `64k`로 낮추고 음성 업로드 두 경로(`= /api/translate/speech`, `= /api/translate/dialog`)에만 `11m`를 둔다(`frontend/nginx.conf`). nginx를 거치지 않고 uvicorn에 바로 닿는 개발 서버에도 같은 한도가 걸리게, 앱도 업로드 두 경로 밖의 요청 본문을 64KiB까지만 받는다(넘으면 413, 넘친 본문은 더 읽지 않는다)
- 64KiB의 근거: 이 앱의 JSON·폼 본문은 가장 커도 수 KB다(refresh 토큰 4,096자 이하, 비밀번호 72바이트 이하, 500자 글자 번역은 모든 글자를 `\uXXXX`로 써도 약 6KB)
- 뒤(실제 앱에 같은 방법): 11MB 본문은 413(응답 38바이트, 최장 정지 24\~137ms), 본문 한도 바로 아래의 목록(65,535바이트)은 422(응답 136바이트, 최장 정지 16\~26ms)

**2. 웹소켓 글 메시지**

- 전: uvicorn 기본 상한(압축을 푼 뒤 16MiB)과 permessage-deflate 때문에, 선로에서 16,328바이트인 첫 메시지가 16,777,215자 글로 풀려 들어왔다(로그인 전, 연결마다). 그 글을 이벤트 루프에서 `json.loads`로 푸는 데 2.16초가 걸렸고, 그 뒤에야 형식 오류로 닫혔다
- 바꾼 것: 글 메시지는 풀기 전에 길이를 본다. 첫 메시지 4,096자, 그 뒤의 제어 메시지 1,024자를 넘으면 `4422`로 닫는다(`backend/app/routers/live.py`). uvicorn은 `--ws-max-size 1048576`으로 메시지 하나를 압축을 푼 뒤 1MiB까지만 받는다(넘으면 `1009`, `backend/Dockerfile`과 README의 개발 서버 명령)
- 근거: 화면이 보내는 가장 긴 첫 메시지는 364자(access 토큰 269자, 두 사람 대화를 다시 연결할 때의 16자리 마디 번호까지)이고 제어 메시지는 53자다(측정 도구의 `json.dumps`로는 373자·58자). 소리는 32ms(1,024바이트)씩 보내고, 서버가 쓰는 가장 큰 메시지는 한 마디 전체(30초, 960,000바이트)다
- permessage-deflate는 끄지 않았고 Origin 확인도 넣지 않았다. 위 상한으로 풀리는 크기가 1MiB에 묶이고, 인증은 첫 메시지의 토큰이라 다른 출처의 페이지가 연결을 열어도 로그인한 사용자로 쓸 수 없다
- 뒤: 같은 16MiB 메시지는 풀린 크기가 1MiB를 넘는 순간 `1009`로 닫혀 앱에 닿지 않는다(2ms). 1MiB 바로 아래(1,048,575자)의 첫 메시지는 실제 앱에서 1ms 만에 `4422`로 닫힌다(같은 글의 `json.loads`는 187ms)

**3. 업로드 음성의 프레임·패킷 수**

- 전: 업로드 검사(`validate_audio`)가 풀린 길이(30초)만 봐서, 표본 하나짜리 프레임으로 채운 짧은 파일이 검사와 인식 전 디코딩에서 모델 스레드를 붙잡았다. 프레임 200,000개(600,626바이트, 4.2초 분량)에 검사 1.77초와 faster-whisper 디코딩 1.43초였고, 10MB 안에는 수백만 개가 들어간다. 풀지 않는 다른 스트림에 작은 패킷을 채워도 같았다(PyAV가 그 패킷도 하나씩 읽어 버리고, 인식 전 디코딩도 같다): 패킷 300,000개(933,029바이트)에 검사는 0.26초 만에 통과했고 디코딩은 1.20초였다
- 바꾼 것: 파일에서 읽은 패킷(모든 스트림)과 풀린 프레임이 각각 15,000개를 넘으면 422 `"Audio could not be decoded"`로 거절한다(`backend/app/services/pipeline.py`). 검사가 인식보다 먼저라, 거절된 파일은 인식 전 디코딩과 두 사람 대화의 언어 판별에 닿지 않는다
- 15,000의 근거(30초당 풀린 프레임 수): 16 kHz WAV 469(측정 입력 FLEURS 1,649개는 최대 478, 서비스 측정에 올린 WAV 120개는 최대 472), 브라우저 녹음 webm·ogg Opus(20ms 프레임) 1,501, mp4 AAC(48 kHz) 1,407, mp3(44.1 kHz) 1,150, FLAC 약 310\~420, 가장 촘촘한 정상 설정인 Opus 2.5ms 프레임 12,000. 그 위에 25% 여유를 두었다. 상한에 딱 맞는 파일을 받아도 검사 약 0.2초와 디코딩 약 0.2초다
- 같은 판정: 측정 입력(FLEURS 1,649개, 서비스 측정 WAV 120개, 합성 음성 WAV 319개)과 여러 형식으로 만든 29.5초·31초 파일 28개에서, 고치기 전후의 판정(통과·30초 초과)과 풀린 프레임 열이 모두 같았다
- 뒤: 프레임 100,000·200,000·1,000,000개 파일은 모두 0.15\~0.16초 만에, 다른 스트림의 패킷 1,000,000개 파일은 0.04초 만에 거절된다. 보통 30초 WAV의 검사는 0.011초다

## CI 워크플로의 토큰 권한과 액션 고정 (2026-11-24)

- 바꾼 것(`.github/workflows/voice-translator.yml`): 맨 위 `permissions: contents: read`, checkout 네 곳에 `persist-credentials: false`, 액션 열두 곳을 태그 대신 커밋 SHA로 부른다(줄 끝 주석이 그 SHA의 릴리스 태그). 작업·단계·명령·경로 필터는 그대로다. 올리는 방법은 그 파일의 머리 주석에 있다
- 이유: main에 push할 때 화면·브라우저 검사 작업의 `npm ci`가 의존성의 설치 스크립트를 돌리고 제3자 액션도 도는데, 그 단계들이 checkout이 `.git/config`에 남긴 토큰을 읽을 수 있었고 토큰 권한은 저장소 기본값을 따랐다. 태그는 다른 커밋으로 옮겨질 수 있다. 같은 저장소의 다른 워크플로와 같은 설정이다
- 이 워크플로에는 토큰으로 저장소에 쓰는 단계가 없다(캐시·결과 올리기는 런타임 토큰을 쓴다). 바꾼 워크플로가 실제 CI에서 도는 것은 아직 확인하지 않았다
